    WebIDE, depuração remota e investigação de APIs no KaiOS 2.5¶

    1. Visão geral¶

    O WebIDE é uma ferramenta de desenvolvimento baseada nas ferramentas de desenvolvedor do Firefox usada para conectar um computador a dispositivos baseados em Gecko/B2G, incluindo aparelhos com KaiOS 2.5.

    No contexto do KaiOS 2.5, ele pode ser utilizado para:

    1. conectar-se ao runtime do aparelho;
    2. instalar e executar aplicações;
    3. abrir as ferramentas de desenvolvimento;
    4. visualizar logs;
    5. executar JavaScript no contexto da aplicação;
    6. inspecionar HTML e CSS;
    7. depurar código JavaScript;
    8. investigar APIs WebAPI expostas pelo runtime;
    9. estudar diferenças entre o ambiente normal de uma aplicação e ambientes privilegiados.

    A documentação oficial do KaiOS para o ambiente 2.x recomenda especificamente o Firefox 59 para o fluxo tradicional de desenvolvimento com WebIDE e descreve a conexão através de ADB e do debugger-socket.

    Este capítulo é particularmente relevante para engenharia reversa e experimentação em aparelhos KaiOS 2.5 com acesso ADB/root, inclusive para investigar projetos antigos como o strukturart/shell-command.

    Há, entretanto, uma distinção importante:

    ADB, root e WebIDE são mecanismos diferentes. Ter acesso root ao shell não significa automaticamente que uma aplicação KaiOS possa executar comandos de shell.

    O objetivo do WebIDE, neste contexto, é justamente permitir investigar o que o runtime JavaScript do aparelho ainda expõe.

    2. Conceitos fundamentais¶

    2.1 Gecko e B2G¶

    O KaiOS 2.5 pertence à família de sistemas derivados do Firefox OS/B2G. Sua plataforma utiliza uma arquitetura baseada em:

    Aplicação HTML/CSS/JavaScript
             │
             ▼
        Gecko / B2G
             │
       WebAPIs / IPC
             │
             ▼
        Serviços do sistema
             │
             ▼
        Linux / Gonk
             │
             ▼
          Hardware

    Isso é importante porque JavaScript executado por uma aplicação não possui automaticamente os mesmos privilégios do shell Linux.

    Uma aplicação pode ter acesso a determinadas APIs dependendo de:

    1. tipo da aplicação;
    2. permissões declaradas no manifesto;
    3. assinatura;
    4. origem;
    5. versão do Gecko;
    6. configuração do firmware;
    7. modificações realizadas pelo fabricante.

    A documentação do KaiOS diferencia aplicações hospedadas, privilegiadas e certificadas. APIs sensíveis podem exigir níveis específicos de privilégio.

    2.2 ADB¶

    O Android Debug Bridge (ADB) é uma ferramenta de comunicação com o dispositivo.

    No KaiOS 2.5, ele é utilizado para tarefas como:

    adb devices

    identificar o aparelho conectado e, quando permitido pelo firmware:

    adb shell

    obter um shell no dispositivo.

    Em aparelhos com root, esse shell pode proporcionar acesso muito mais amplo ao sistema operacional.

    Porém:

    ADB shell
   ≠
JavaScript da aplicação

    São ambientes diferentes.

    2.3 WebIDE¶

    O WebIDE funciona como uma interface de desenvolvimento para o runtime Gecko/B2G.

    O fluxo tradicional é:

    Computador
    │
    │ USB
    ▼
   ADB
    │
    │ debugger socket
    ▼
KaiOS / Gecko
    │
    ▼
Aplicação
    │
    ▼
Developer Tools

    A documentação oficial mostra a utilização do socket:

    adb root
adb forward tcp:6000 localfilesystem:/data/local/debugger-socket

    Esse comando cria um encaminhamento entre a porta TCP 6000 do computador e o socket local de debugging do aparelho.

    2.4 Console¶

    O Console das Developer Tools permite executar JavaScript no contexto do alvo selecionado.

    A documentação do KaiOS descreve explicitamente o Console como uma ferramenta que permite visualizar informações de uma página e executar expressões JavaScript no contexto dela.

    Isso é especialmente útil para responder perguntas como:

    typeof navigator

    ou:

    Object.keys(navigator)

    e investigar quais APIs estão realmente presentes naquele aparelho.

    3. Como funciona¶

    3.1 Fluxo de conexão¶

    O procedimento tradicional pode ser representado assim:

    KaiOS
  │
  ├── modo debugging
  │
  ▼
ADB
  │
  ├── adb devices
  │
  ├── adb root
  │
  └── adb forward
          │
          ▼
   debugger-socket
          │
          ▼
       WebIDE
          │
          ▼
  Developer Tools
          │
          ├── Inspector
          ├── Console
          ├── Debugger
          └── Scratchpad

    O KaiOS documenta esse fluxo para dispositivos 2.x.

    3.2 Socket de debugging¶

    O caminho documentado para KaiOS 2.5 é:

    /data/local/debugger-socket

    O encaminhamento pode ser feito com:

    adb forward tcp:6000 localfilesystem:/data/local/debugger-socket

    A partir desse momento, o computador pode acessar o endpoint através de:

    localhost:6000

    No WebIDE, seleciona-se Remote Runtime e informa-se:

    localhost:6000

    A documentação do KaiOS também confirma que a porta TCP pode ser alterada.

    4. Componentes envolvidos¶

    Componente Função
    ADB Comunicação entre computador e aparelho
    adb shell Acesso ao shell Linux
    adb root Solicita daemon ADB com privilégios de root, quando suportado
    adb forward Encaminha uma porta/socket do dispositivo
    debugger-socket Endpoint utilizado pelas ferramentas de debugging
    WebIDE Interface de desenvolvimento
    Developer Tools Inspector, Console, Debugger etc.
    Gecko/B2G Runtime das aplicações
    manifest.webapp Define informações e permissões da aplicação
    JavaScript Código executado pela aplicação

    5. Procedimentos práticos¶

    5.1 Verificar se o ADB reconhece o aparelho¶

    Objetivo: confirmar que a comunicação básica funciona antes de investigar o WebIDE.

    Pré-requisitos:

    1. KaiOS 2.5;
    2. modo de debugging habilitado;
    3. cabo USB com transmissão de dados;
    4. ADB instalado.

    Execute:

    adb devices

    Resultado esperado:

    List of devices attached
XXXXXXXX    device

    Se aparecer:

    unauthorized

    o aparelho ainda não autorizou a conexão.

    Se a lista estiver vazia:

    List of devices attached

    o problema ainda está no nível de ADB/USB/debugging, não no WebIDE.

    5.2 Verificar o shell¶

    Execute:

    adb shell

    Depois:

    id

    O resultado pode ser algo semelhante a:

    uid=0(root) gid=0(root)

    ou:

    uid=2000(shell) gid=2000(shell)

    Isso permite determinar imediatamente se o shell ADB está sendo executado como root.

    Importante: possuir uid=0 aqui não significa que o JavaScript de uma aplicação também possuirá privilégios equivalentes.

    5.3 Criar o encaminhamento do debugger¶

    Em aparelhos nos quais o mecanismo tradicional permanece disponível:

    adb root
adb forward tcp:6000 localfilesystem:/data/local/debugger-socket

    Depois verifique os encaminhamentos:

    adb forward --list

    O resultado deverá indicar um encaminhamento envolvendo a porta 6000.

    Se adb root retornar uma mensagem indicando que o dispositivo não permite root ADB, isso não significa necessariamente que o aparelho não tenha root por outros meios.

    5.4 Abrir o WebIDE¶

    Em ambientes compatíveis, abra uma versão do Firefox que ainda possua WebIDE.

    A documentação histórica do KaiOS recomenda Firefox 59 para o ambiente KaiOS 2.x.

    No Firefox, procure:

    Tools
  → Web Developer
      → WebIDE

    Em algumas versões, o atalho utilizado é:

    Shift + F8

    A interface deverá apresentar opções relacionadas a runtimes.

    Selecione:

    Remote Runtime

    e informe:

    localhost:6000

    A documentação oficial descreve exatamente esse mecanismo de conexão.

    5.5 Abrir as Developer Tools¶

    Depois de conectar o runtime, selecione uma aplicação.

    O WebIDE permite executar a aplicação e abrir as ferramentas através do botão representado por uma chave inglesa.

    Entre as ferramentas disponíveis estão:

    1. Inspector;
    2. Console;
    3. JavaScript Debugger;
    4. Style Editor;
    5. Scratchpad.

    O ponto mais importante para a investigação deste capítulo é o Console.

    6. Investigação das APIs JavaScript¶

    6.1 Não presumir que uma API existe¶

    Uma abordagem inadequada seria simplesmente executar:

    navigator.mozSystem

    e concluir que o resultado determina se o KaiOS pode executar comandos.

    Isso é insuficiente.

    A existência de uma propriedade não demonstra que:

    1. ela pode executar comandos;
    2. ela está disponível para aquele tipo de aplicação;
    3. ela possui os privilégios necessários;
    4. o firmware implementa o comportamento esperado;
    5. o código antigo do shell-command é compatível com aquele runtime.

    O teste correto começa pela descoberta.

    6.2 Inspecionar navigator¶

    No Console:

    typeof navigator

    Depois:

    Object.keys(navigator)

    Dependendo da implementação do Gecko, APIs nativas podem não aparecer exatamente da mesma maneira que propriedades JavaScript comuns. Portanto, também é útil testar propriedades individualmente.

    Por exemplo:

    typeof navigator.mozTCPSocket

    A documentação do KaiOS confirma a existência histórica de navigator.mozTCPSocket e sua relação com a API de sockets TCP.

    6.3 Pesquisar APIs relacionadas ao sistema¶

    Pode-se procurar propriedades relacionadas a APIs Mozilla/B2G:

    Object.getOwnPropertyNames(navigator).sort()

    E pesquisar visualmente por nomes contendo:

    moz
system
process
shell
exec
socket
device

    Também é possível verificar diretamente:

    typeof navigator.mozProcess

    e:

    typeof navigator.mozSystem

    Porém, esses testes devem ser tratados como investigação, não como prova de compatibilidade com shell-command.

    7. O projeto strukturart/shell-command¶

    O projeto investigado nesta seção é descrito como:

    "Execute shell commands from javascript level"

    O repositório aparece catalogado como um projeto relacionado a KaiOS, com aproximadamente 157 KB de código e histórico de desenvolvimento iniciado na época do KaiOS 2.x.

    Existe uma evidência particularmente importante sobre sua compatibilidade histórica.

    Em uma discussão sobre KaiOS, o próprio autor do projeto afirmou que até o KaiOS 2.4 era possível executar scripts shell a partir do JavaScript, apresentando o repositório strukturart/shell-command como demonstração dessa abordagem.

    Isso fornece uma hipótese de investigação muito mais sólida:

    KaiOS 2.4
   │
   └── mecanismo usado pelo shell-command
             │
             ▼
KaiOS 2.5
   │
   ├── mecanismo removido?
   ├── mecanismo restringido?
   ├── API ainda existente?
   ├── privilégio diferente?
   └── alteração no Gecko?

    Portanto, não se deve assumir que o projeto funcionará simplesmente porque o aparelho possui root.

    8. Procedimento recomendado para testar shell-command¶

    8.1 Objetivo¶

    Determinar se o mecanismo utilizado pelo projeto histórico continua funcional em um aparelho KaiOS 2.5.

    8.2 Pré-requisitos¶

    1. aparelho KaiOS 2.5;
    2. ADB funcional;
    3. acesso root, preferencialmente;
    4. WebIDE funcional;
    5. cópia local do repositório;
    6. possibilidade de instalar uma aplicação experimental.

    8.3 Primeira etapa: preservar o código original¶

    Clone o projeto no computador:

    git clone https://github.com/strukturart/shell-command.git

    Entre no diretório:

    cd shell-command

    Antes de modificar qualquer coisa, registre:

    git status

    e:

    git log --oneline --all

    O objetivo é preservar o estado original para que os testes possam ser reproduzidos.

    8.4 Segunda etapa: identificar o mecanismo utilizado¶

    Antes de instalar o projeto, procure referências a APIs de execução de processos:

    grep -RniE 'mozProcess|mozSystem|process|exec|shell|command' .

    Também é útil:

    find . -maxdepth 2 -type f -print

    e:

    cat manifest.webapp

    O objetivo é descobrir qual API o projeto realmente utiliza, em vez de assumir que utiliza navigator.mozSystem.

    8.5 Terceira etapa: testar a API isoladamente¶

    Antes de executar o projeto inteiro, crie uma aplicação mínima que apenas investigue a API.

    Por exemplo, o JavaScript pode registrar:

    console.log("navigator.mozProcess =", typeof navigator.mozProcess);
console.log("navigator.mozSystem =", typeof navigator.mozSystem);
console.log("navigator.mozTCPSocket =", typeof navigator.mozTCPSocket);

    Depois abra o Console do WebIDE.

    Isso produz uma matriz inicial:

    API Resultado Interpretação
    mozProcess undefined API não exposta nesse contexto
    mozProcess object API aparentemente presente
    mozProcess function API presente como função
    mozSystem undefined não disponível nesse contexto
    mozTCPSocket object API TCP disponível, sujeito a permissões

    A interpretação definitiva depende do contexto da aplicação e do firmware.

    9. Investigação de permissões¶

    A presença de uma API não é suficiente.

    O manifesto da aplicação pode conter permissões:

    "permissions": {
    "tcp-socket": {}
}

    Por exemplo, a documentação do KaiOS identifica tcp-socket como uma permissão associada à API TCP e indica que ela requer aplicação privilegiada.

    O mesmo princípio deve ser aplicado ao mecanismo utilizado pelo shell-command.

    Portanto, ao analisar o projeto, deve-se registrar:

    manifest.webapp
        │
        ├── type
        ├── permissions
        ├── origin
        └── outras propriedades

    Uma aplicação comum, privilegiada e certificada pode possuir capacidades diferentes.

    10. Exemplos de investigação¶

    Exemplo 1: determinar o contexto JavaScript¶

    console.log(location.href);
console.log(document.location.origin);
console.log(typeof navigator);

    Isso ajuda a identificar onde o código está sendo executado.

    Exemplo 2: procurar APIs Mozilla¶

    Object.getOwnPropertyNames(navigator)
    .filter(function (name) {
        return name.toLowerCase().indexOf("moz") !== -1;
    })
    .sort();

    O resultado fornece uma lista de propriedades relacionadas ao namespace Mozilla que o objeto expõe naquele contexto.

    Exemplo 3: testar uma API específica sem executá-la¶

    typeof navigator.mozProcess

    Isso é deliberadamente um teste de existência, não uma tentativa de executar comandos.

    Essa abordagem é preferível durante a fase inicial de investigação porque reduz o risco de efeitos colaterais.

    11. Problemas comuns¶

    11.1 O aparelho aparece no adb devices, mas não no WebIDE¶

    Possíveis causas:

    1. socket de debugging não encaminhado;
    2. caminho do socket diferente;
    3. runtime incompatível;
    4. versão inadequada do Firefox;
    5. configuração de debugging desabilitada;
    6. restrição específica do firmware.

    O primeiro teste deve ser:

    adb forward --list

    Depois:

    adb forward tcp:6000 localfilesystem:/data/local/debugger-socket

    11.2 O WebIDE mostra um aviso sobre versão do runtime¶

    Esse comportamento pode ocorrer porque o Gecko do dispositivo possui uma data/build diferente da versão do Firefox usada pelo WebIDE.

    A documentação do KaiOS orienta que determinado aviso de runtime antigo pode ser ignorado no fluxo documentado para KaiOS 2.x.

    Isso não significa, entretanto, que qualquer incompatibilidade possa ser ignorada. Se as Developer Tools não funcionarem, a versão do runtime passa a ser uma variável relevante.

    11.3 O Console funciona, mas a API não existe¶

    Isso é perfeitamente possível.

    O Console apenas demonstra que o mecanismo de debugging funciona. Ele não garante que uma determinada WebAPI esteja disponível.

    Por exemplo:

    typeof navigator.mozProcess

    pode retornar:

    "undefined"

    mesmo quando:

    ADB
root
WebIDE

    estão funcionando normalmente.

    11.4 A API existe, mas a operação falha¶

    Nesse caso é necessário separar:

    API inexistente
      ↓
API existente
      ↓
permissão insuficiente
      ↓
API permitida
      ↓
implementação diferente
      ↓
operação executada

    O erro do Console deve ser preservado integralmente para investigação posterior.

    12. Diagnóstico e debugging¶

    Uma investigação adequada deve registrar pelo menos:

    adb shell getprop

    versão do sistema:

    adb shell getprop | grep -i kai

    informações do dispositivo:

    adb shell getprop | grep -Ei 'ro.product|ro.build'

    e:

    adb shell id

    Também é útil registrar:

    adb forward --list

    Além disso, a aplicação experimental deve registrar no Console:

    console.log("User agent:", navigator.userAgent);
console.log("Location:", location.href);

    Essas informações ajudam a diferenciar:

    1. aparelho;
    2. firmware;
    3. runtime;
    4. contexto da aplicação;
    5. permissões;
    6. disponibilidade da API.

    13. Segurança e riscos¶

    13.1 Root não deve ser tratado como requisito suficiente¶

    Um aparelho com root permite alterar componentes que uma aplicação normal não poderia modificar.

    Isso aumenta consideravelmente o risco de:

    1. apagar arquivos importantes;
    2. alterar permissões;
    3. modificar aplicações do sistema;
    4. causar bootloop;
    5. inutilizar componentes do sistema;
    6. perder a possibilidade de atualização;
    7. necessitar de reflashing do firmware.

    13.2 Evitar testes destrutivos inicialmente¶

    Na primeira fase, não utilizar comandos como:

    rm -rf

    nem modificar diretamente partições ou diretórios críticos.

    O primeiro objetivo deve ser somente:

    descobrir
    ↓
observar
    ↓
registrar
    ↓
testar API
    ↓
testar operação inofensiva

    Somente depois disso deve-se considerar modificações persistentes.

    13.3 Preservar evidências¶

    Antes de alterar o aparelho, registre:

    adb shell getprop > getprop.txt
adb shell id > id.txt
adb forward --list > adb-forward.txt

    Também é recomendável manter uma cópia do firmware original e dos arquivos modificados antes de qualquer alteração.

    14. Compatibilidade¶

    Componente Dependência
    WebIDE Versão do Firefox e compatibilidade com Gecko
    ADB Firmware, modo debugging e implementação do fabricante
    debugger-socket Configuração do runtime
    WebAPIs Versão do Gecko/KaiOS
    permissões Tipo da aplicação e manifesto
    shell-command API utilizada pelo projeto e compatibilidade do runtime
    root Método de root e firmware
    caminho de sockets Pode variar entre builds
    aparelhos KaiOS 2.5 Fabricantes podem modificar o sistema

    A própria documentação do KaiOS recomenda Firefox 59 para o ambiente de desenvolvimento 2.x, enquanto versões posteriores da plataforma possuem ferramentas e runtimes diferentes.

    Também há evidência de que o ecossistema evoluiu significativamente depois do KaiOS 2.5. O KaiOS 3.0, por exemplo, passou para Gecko 84 e alterou diversas APIs e mecanismos de gerenciamento de aplicações.

    Portanto, resultados obtidos no KaiOS 3.x ou 4.x não devem ser automaticamente aplicados ao KaiOS 2.5.

    15. Referências cruzadas¶

    Este capítulo possui relação direta com:

    1. Arquitetura do KaiOS
    2. Gecko, B2G e Gonk
    3. ADB e comunicação com o dispositivo
    4. Root e privilégios
    5. Estrutura de aplicações KaiOS
    6. Manifestos e permissões
    7. WebAPIs do KaiOS
    8. Engenharia reversa de aplicações
    9. Debugging e análise de logs
    10. Modificação do sistema e firmware

    Em particular, a investigação do shell-command depende de uma compreensão anterior de tipos de aplicações e permissões.

    16. Resumo¶

    O WebIDE constitui uma ponte entre o computador e o runtime Gecko do KaiOS, permitindo executar e depurar aplicações e investigar as APIs efetivamente disponibilizadas pelo aparelho.

    O fluxo básico é:

    ADB
 ↓
debugger-socket
 ↓
WebIDE
 ↓
Developer Tools
 ↓
Console
 ↓
investigação do runtime

    Para a investigação do strukturart/shell-command, a metodologia recomendada é não começar tentando executar comandos shell.

    O procedimento mais seguro e tecnicamente informativo é:

    1. Confirmar ADB
    2. Confirmar shell/root

    Um dado histórico particularmente relevante é que o próprio autor do shell-command associou sua técnica ao KaiOS até a versão 2.4. Isso torna o KaiOS 2.5 um excelente objeto de investigação de compatibilidade, mas não permite concluir antecipadamente que a técnica continuará funcionando.

    Esta seção deverá ser conectada posteriormente aos capítulos de ADB, root, arquitetura Gecko/B2G, aplicações e manifestos, WebAPIs, engenharia reversa e debugging.

    Durante a compilação final do manual, devem ser verificadas especificamente:

    1. o caminho exato do debugger-socket no firmware analisado;
    2. a versão exata do Gecko do aparelho;
    3. quais APIs utilizadas pelo shell-command ainda existem no KaiOS 2.5;
    4. quais permissões são necessárias;
    5. se o comportamento muda entre fabricantes e chipsets;
    6. se a técnica histórica do projeto funciona no firmware específico testado;
    7. se aparelhos mais recentes da linha KaiOS 2.5 possuem restrições adicionais de debugging.
