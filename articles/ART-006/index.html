    Dropbear/Beardrop no Zapp II: compilação e uso de SSH¶

    1. Visão geral¶

    O Dropbear é uma implementação leve dos protocolos SSH, adequada para sistemas embarcados. No contexto do Zapp II, ele pode ser utilizado para disponibilizar acesso remoto ao shell do aparelho quando já existe uma forma de obter root, por exemplo, através de ADB e de um su funcional [cite: 3].

    Neste contexto, é importante distinguir três elementos:

    Componente Função
    dropbear Servidor SSH
    dbclient Cliente SSH do Dropbear
    dropbearkey Geração de chaves privadas do servidor
    scp Transferência de arquivos via SSH
    dropbearconvert Conversão entre formatos de chaves

    O termo Beardrop não deve ser tratado automaticamente como um componente diferente do Dropbear. É necessário identificar exatamente qual projeto ou binário está sendo chamado de Beardrop antes de assumir compatibilidade [cite: 3].

    Para o Zapp II, o objetivo mais simples é produzir um dropbear ARMv7 estático, transferi-lo para o aparelho e executá-lo manualmente [cite: 3].

    2. Conceitos fundamentais¶

    2.1 Cross-compilação¶

    O computador utilizado para compilação provavelmente é x86_64, enquanto o Zapp II utiliza uma arquitetura ARM [cite: 3].

    Assim:

    PC x86_64
   │
   │ cross-compiler
   ▼
binário ARM
   │
   ▼
Zapp II

    O comando utilizado anteriormente:

    ./configure --host=arm-linux-gnueabihf --enable-static

    informa ao sistema de compilação que o programa será executado em uma plataforma ARM com ABI gnueabihf [cite: 3].

    Isso não significa automaticamente que o binário será compatível com o Zapp II. A arquitetura, ABI, CPU, libc e demais características precisam ser compatíveis [cite: 3].

    2.2 Por que o make falhou¶

    O erro apresentado foi:

    configure: error: *** zlib missing - install first or check config.log ***

    O ponto mais importante é que o problema ocorreu durante o configure [cite: 3].

    Consequentemente:

    make PROGRAMS="dropbear dbclient dropbearkey scp"

    produziu:

    make: *** No targets specified and no makefile found. Stop.

    Isso é uma consequência, não um segundo problema independente [cite: 3].

    O fluxo foi:

    ./configure
      │
      ├── procura zlib
      │
      ├── zlib não encontrada
      │
      └── configure aborta
              │
              ▼
        Makefile não criado
              │
              ▼
             make
              │
              └── falha

    Portanto, não adianta executar make novamente enquanto o configure continuar falhando [cite: 3].

    3. Como funciona a dependência do zlib¶

    O Dropbear pode ser compilado sem suporte a zlib. Para um servidor SSH minimalista em um aparelho embarcado, essa é uma opção particularmente interessante [cite: 3].

    Há exemplos de builds ARMv7 estáticos do Dropbear utilizando explicitamente:

    • --disable-zlib [cite: 3]
    • --enable-static [cite: 3]

    inclusive combinados com outras opções destinadas a reduzir dependências do sistema [cite: 3].

    Portanto, no seu caso, não é necessário instalar zlib apenas para obter um servidor SSH funcional [cite: 3].

    4. Procedimento prático: recompilar o Dropbear¶

    4.1 Objetivo¶

    Produzir um Dropbear estático para ARM e evitar a dependência do zlib [cite: 3].

    4.2 Pré-requisitos¶

    No computador de compilação:

    • Código-fonte do Dropbear [cite: 3]
    • Compilador arm-linux-gnueabihf-gcc [cite: 3]
    • binutils correspondentes [cite: 3]
    • Ambiente de compilação GNU [cite: 3]
    • Ferramentas necessárias pelo próprio projeto [cite: 3]

    No seu ambiente, o compilador já foi encontrado:

    checking for arm-linux-gnueabihf-gcc... arm-linux-gnueabihf-gcc

    Portanto, essa parte está funcionando [cite: 3].

    4.3 Limpar uma configuração parcialmente criada¶

    Entre no diretório do Dropbear:

    cd ~/dropbear

    Se você estiver reutilizando a árvore de compilação após uma tentativa malsucedida:

    make distclean 2>/dev/null || true

    Se o projeto ainda não tiver produzido um Makefile, o erro de distclean pode ser ignorado [cite: 3]. Também é possível simplesmente trabalhar em uma cópia limpa do código-fonte [cite: 3].

    4.4 Configurar sem zlib¶

    Execute:

    ./configure     --host=arm-linux-gnueabihf     --enable-static     --disable-zlib

    O ponto essencial é: --disable-zlib [cite: 3]. A configuração deve prosseguir além do ponto em que anteriormente apareceu: *** zlib missing [cite: 3].

    4.5 Compilar somente os componentes necessários¶

    Depois que o configure terminar sem erro, execute:

    make PROGRAMS="dropbear dbclient dropbearkey scp"

    Uma configuração semelhante é utilizada em builds ARMv7 estáticos documentados publicamente [cite: 3]. Se o objetivo for apenas disponibilizar um servidor SSH no Zapp II, o componente fundamental é: dropbear e, para criar as chaves: dropbearkey [cite: 3].

    Portanto, uma compilação ainda mais minimalista pode ser considerada:

    make PROGRAMS="dropbear dropbearkey"

    A disponibilidade exata dos alvos depende da versão do Dropbear utilizada [cite: 3].

    5. Verificar o binário antes de transferi-lo¶

    Não copie imediatamente o arquivo para o telefone [cite: 3]. Primeiro descubra o que foi produzido:

    file dropbear

    Um resultado desejável seria algo indicando ARM e executável estático, por exemplo:

    ELF 32-bit LSB executable, ARM, ...
statically linked

    O texto exato varia conforme a versão das ferramentas [cite: 3].

    Também é útil:

    arm-linux-gnueabihf-readelf -h dropbear

    Verifique principalmente:

    Class:       ELF32
Machine:     ARM

    E:

    arm-linux-gnueabihf-readelf -d dropbear

    Se o executável for realmente estático, não deverá haver uma lista normal de bibliotecas dinâmicas em NEEDED [cite: 3].

    Outra verificação útil:

    arm-linux-gnueabihf-strip dropbear

    Isso reduz o tamanho do executável removendo informações que não são necessárias para sua execução [cite: 3]. Antes de fazer isso, entretanto, é recomendável manter uma cópia do binário não reduzido para debugging [cite: 3].

    6. Confirmar a arquitetura do Zapp II¶

    A arquitetura do compilador não deve ser escolhida apenas porque o aparelho possui ARM [cite: 3]. No caso do Zapp II, é importante confirmar a arquitetura efetivamente utilizada pelo firmware [cite: 3].

    No aparelho, com shell disponível:

    uname -a
uname -m

    Também pode ser útil:

    cat /proc/cpuinfo

    Procure informações como:

    • Processor
    • CPU architecture
    • Hardware
    • Features

    O objetivo é determinar se o binário ARMv7 produzido é compatível com o processador e com a ABI utilizada pelo sistema [cite: 3].

    Importante: ARMv7 e arm-linux-gnueabihf não são sinônimos. A arquitetura da CPU e a ABI utilizada pelo executável são questões relacionadas, mas distintas. Por isso, o teste real no aparelho é indispensável [cite: 3].

    7. Transferir o Dropbear para o Zapp II¶

    Com ADB funcionando:

    adb push dropbear /data/local/tmp/dropbear
adb push dropbearkey /data/local/tmp/dropbearkey

    Depois:

    adb shell

    No aparelho:

    su
chmod 755 /data/local/tmp/dropbear
chmod 755 /data/local/tmp/dropbearkey

    Verifique:

    ls -l /data/local/tmp/dropbear*

    8. Primeiro teste do executável¶

    Antes de tentar iniciar o servidor, execute:

    /data/local/tmp/dropbear -h

    O objetivo é confirmar que o kernel conseguiu carregar o ELF [cite: 3].

    Se aparecer a ajuda do Dropbear, isso já confirma várias coisas:

    ELF compatível
        ↓
loader capaz de executá-lo
        ↓
Dropbear iniciou
        ↓
opções de linha de comando disponíveis

    Se aparecer not found, isso não significa necessariamente que o arquivo não existe [cite: 3]. Pode significar que o kernel não conseguiu encontrar o interpretador/loader necessário para um executável dinâmico [cite: 3]. Esse é um dos motivos pelos quais um binário realmente estático é interessante nesse cenário [cite: 3].

    9. Geração da chave do servidor¶

    O servidor SSH precisa de uma chave de host [cite: 3]. Crie um diretório persistente:

    mkdir -p /data/ssh

    Depois:

    /data/local/tmp/dropbearkey     -t ed25519     -f /data/ssh/dropbear_ed25519_host_key

    Se a versão do Dropbear utilizada não aceitar Ed25519, será necessário utilizar um tipo de chave suportado por aquela versão, por exemplo RSA [cite: 3].

    Nesse caso:

    /data/local/tmp/dropbearkey     -t rsa     -f /data/ssh/dropbear_rsa_host_key

    Não se deve assumir que todos os tipos de chave são suportados por todas as versões do Dropbear [cite: 3].

    10. Iniciar o servidor¶

    Para um primeiro teste, é melhor utilizar uma porta diferente de 22, por exemplo:

    /data/local/tmp/dropbear     -r /data/ssh/dropbear_ed25519_host_key     -p 2222
    • A opção -r especifica a chave privada do host [cite: 3].
    • A opção -p 2222 faz o servidor escutar na porta 2222 [cite: 3].

    Uma porta não privilegiada também evita algumas questões relacionadas à tentativa de utilizar a porta 22 durante os testes [cite: 3].

    11. Descobrir o endereço IP¶

    No Zapp II:

    ip addr

    Se houver suporte:

    ip addr show wlan0

    Também pode ser possível utilizar:

    ifconfig

    dependendo das ferramentas disponíveis no firmware [cite: 3]. O resultado deverá permitir identificar algo semelhante a:

    inet 192.168.1.123/24

    Nesse exemplo, o endereço seria 192.168.1.123 [cite: 3].

    12. Conectar a partir do computador¶

    No Linux:

    ssh -p 2222 root@192.168.1.123

    Substitua o endereço pelo IP real do Zapp II [cite: 3]. O primeiro acesso deverá envolver a verificação da chave de host [cite: 3].

    Atenção ao usuário¶

    Não é correto assumir universalmente que o usuário SSH será root [cite: 3]. O Dropbear pode iniciar o processo com determinado usuário dependendo da forma como o servidor foi executado e das opções da versão utilizada [cite: 3].

    Como você está investigando um aparelho com acesso root, primeiro confirme no próprio aparelho:

    id
whoami

    Isso informa qual identidade está sendo utilizada pelo shell atual, mas ainda não prova sozinho qual usuário será aceito pelo servidor SSH [cite: 3]. Esse comportamento deve ser testado no firmware específico do Zapp II [cite: 3].

    13. Diagnóstico¶

    13.1 O configure continua reclamando de zlib¶

    Verifique se a opção foi realmente passada:

    ./configure --help | grep -i zlib

    Se a versão do Dropbear oferecer a opção, deverá existir alguma referência ao suporte a zlib [cite: 3].

    Então execute novamente:

    ./configure     --host=arm-linux-gnueabihf     --enable-static     --disable-zlib

    Se ainda houver erro, examine:

    grep -i zlib config.log

    O config.log é especialmente importante porque mostra os testes realizados pelo configure [cite: 3].

    13.2 make diz que não existe Makefile¶

    Isso normalmente significa que o configure não terminou com sucesso [cite: 3].

    Verifique primeiro:

    ls -l Makefile

    Se não existir, não continue tentando diferentes comandos make [cite: 3]. Primeiro corrija:

    ./configure ...

    Depois confirme:

    ls -l Makefile

    Somente então:

    make

    13.3 O binário não executa no Zapp II¶

    Execute:

    file /data/local/tmp/dropbear

    No PC, também:

    file dropbear

    Depois:

    uname -m

    no Zapp II, e:

    cat /proc/cpuinfo

    Essas informações devem ser comparadas [cite: 3].

    13.4 Permission denied¶

    Verifique:

    ls -l /data/local/tmp/dropbear
chmod 755 /data/local/tmp/dropbear

    Se ainda ocorrer Permission denied, pode haver uma restrição do filesystem ou do SELinux [cite: 3]. Verifique:

    getenforce

    se esse comando estiver disponível [cite: 3].

    Também:

    mount

    pode revelar se o local onde o arquivo foi colocado possui alguma opção que impeça execução [cite: 3].

    13.5 O servidor inicia mas não aceita conexão¶

    Primeiro confirme que o processo está rodando:

    ps | grep dropbear

    Depois verifique sockets:

    netstat -ln

    ou, se disponível:

    ss -ln

    Procure a porta 2222 [cite: 3].

    Também é possível testar localmente no próprio aparelho, caso exista cliente TCP adequado [cite: 3]. A partir do PC:

    nc -vz 192.168.1.123 2222

    Se a porta não estiver acessível, o problema ainda não é autenticação SSH. Primeiro deve ser investigada a conectividade de rede [cite: 3].

    14. Execução em foreground durante debugging¶

    Durante a investigação inicial, não é recomendável iniciar o Dropbear em background imediatamente [cite: 3]. É preferível executar o servidor diretamente no shell:

    /data/local/tmp/dropbear     -r /data/ssh/dropbear_ed25519_host_key     -p 2222

    Assim, mensagens de erro podem permanecer visíveis no terminal [cite: 3]. Somente depois que a execução estiver comprovada faz sentido automatizar a inicialização [cite: 3].

    15. Persistência das chaves¶

    Um detalhe importante para o Zapp II é o local da chave [cite: 3]. Se a chave for criada em /data/ssh/ e esse armazenamento for persistente no firmware, ela poderá sobreviver a reinicializações [cite: 3]. Se for criada em um diretório temporário, a chave poderá desaparecer [cite: 3].

    Isso é importante porque a chave de host identifica criptograficamente o servidor [cite: 3]. Se ela mudar a cada boot, o computador cliente poderá apresentar avisos de alteração da chave conhecida [cite: 3]. Portanto, para uma instalação permanente, deve-se investigar quais partições e diretórios do Zapp II são persistentes [cite: 3].

    16. Segurança¶

    Executar um servidor SSH em um telefone KaiOS com root transforma o aparelho em um serviço de administração remota [cite: 3]. Isso possui consequências importantes [cite: 3].

    Riscos principais¶

    Risco Consequência
    Exposição à rede Terceiros podem tentar conectar
    Shell como root Comprometimento pode significar controle completo
    Chave privada exposta Identidade do servidor pode ser comprometida
    Binário incompatível Crash ou comportamento imprevisível
    Alteração de boot Possível bootloop
    Modificação de /system Pode impedir inicialização
    SELinux inadequado Servidor pode não funcionar
    Firmware específico Comandos podem não ser reproduzíveis em outro aparelho

    Durante a fase experimental, recomenda-se:

    1. Utilizar uma porta de teste [cite: 3];
    2. Manter o servidor desativado quando não estiver sendo utilizado [cite: 3];
    3. Não expor a porta diretamente à Internet [cite: 3];
    4. Preservar uma cópia do firmware original [cite: 3];
    5. Trabalhar inicialmente em /data/local/tmp [cite: 3];
    6. Evitar modificar /system até que o funcionamento esteja comprovado [cite: 3].

    17. Por que não começar modificando o boot¶

    É tentador criar imediatamente um mecanismo para iniciar o Dropbear automaticamente [cite: 3]. Isso deve ser evitado na primeira fase [cite: 3].

    A sequência mais segura é:

    1. Compilar
       ↓
2. Verificar ELF
       ↓
3. Transferir
       ↓
4. Executar manualmente
       ↓
5. Gerar chave
       ↓
6. Iniciar servidor
       ↓
7. Conectar via SSH
       ↓
8. Testar estabilidade
       ↓
9. Investigar persistência
       ↓
10. Só então automatizar

    Essa abordagem preserva a capacidade de recuperação caso alguma etapa apresente problemas [cite: 3].

    18. Configuração recomendada para a investigação do Zapp II¶

    Para o estágio atual da investigação, uma configuração razoável é:

    ./configure     --host=arm-linux-gnueabihf     --enable-static     --disable-zlib

    seguida por:

    make PROGRAMS="dropbear dropbearkey"

    Depois:

    file dropbear
arm-linux-gnueabihf-readelf -h dropbear

    Somente depois de confirmar o binário:

    adb push dropbear /data/local/tmp/dropbear
adb push dropbearkey /data/local/tmp/dropbearkey

    No Zapp II:

    su
chmod 755 /data/local/tmp/dropbear*

    Teste:

    /data/local/tmp/dropbear -h

    E somente então:

    mkdir -p /data/ssh

/data/local/tmp/dropbearkey     -t ed25519     -f /data/ssh/dropbear_ed25519_host_key

    Finalmente:

    /data/local/tmp/dropbear     -r /data/ssh/dropbear_ed25519_host_key     -p 2222

    Essa sequência é adequada como procedimento experimental, mas os parâmetros de arquitetura, ABI, tipo de chave e comportamento de autenticação precisam ser confirmados contra o firmware específico do Zapp II [cite: 3].

    19. Compatibilidade¶

    A compatibilidade deve ser analisada em várias camadas [cite: 3]:

    Camada O que verificar
    Hardware SoC e arquitetura ARM
    CPU Instruções suportadas
    ABI gnueabihf, musleabihf etc.
    libc glibc, musl, Bionic ou outra
    Kernel Recursos de rede e execução ELF
    SELinux Políticas aplicadas ao processo
    KaiOS Versão e personalizações do fabricante
    Firmware Alterações específicas do Zapp II
    Dropbear Versão utilizada
    SSH Algoritmos habilitados

    Especialmente importante é não concluir que um binário Alpine ARMv7 será automaticamente executável no Zapp II [cite: 3]. Alpine normalmente utiliza musl, enquanto dispositivos baseados em Android/B2G podem possuir outro ambiente de runtime [cite: 3]. Para um binário realmente estático, parte dessa diferença é eliminada, mas não necessariamente todas as incompatibilidades [cite: 3].

    Posteriormente, esta seção poderá servir de base para um capítulo específico sobre acesso remoto e administração do Zapp II [cite: 3].

    Durante a compilação final do manual, devem ser verificadas especificamente:

    1. Arquitetura e ABI exatas do Zapp II [cite: 3];
    2. Versão do kernel [cite: 3];
    3. libc/runtime efetivamente utilizado [cite: 3];
    4. Versão do KaiOS [cite: 3];
    5. Versão do Dropbear utilizada nos testes [cite: 3];

    7. Comportamento de autenticação do Dropbear nesse firmware [cite: 3];
    8. Políticas SELinux [cite: 3];
    9. Persistência de /data [cite: 3];
    10. Possibilidade de inicialização automática sem modificar componentes críticos do firmware [cite: 3].

    21. Resumo¶

    O erro apresentado durante a compilação não indica um problema com o make [cite: 3]. O problema ocorreu anteriormente, quando o configure detectou a ausência de zlib e abortou [cite: 3].

    Para o objetivo específico de disponibilizar SSH no Zapp II, a abordagem mais simples é recompilar o Dropbear com:

    ./configure     --host=arm-linux-gnueabihf     --enable-static     --disable-zlib

    e então:

    make PROGRAMS="dropbear dropbearkey"

    O binário deve ser verificado no computador antes de ser transferido ao aparelho [cite: 3]. Depois, deve ser executado inicialmente de forma manual em /data/local/tmp, com uma chave armazenada em /data/ssh e uma porta de teste como 2222 [cite: 3].

    A principal conclusão técnica é que não é necessário resolver a dependência de zlib para obter um Dropbear funcional, desde que a versão utilizada ofereça a opção --disable-zlib [cite: 3]. Builds ARMv7 estáticos utilizando exatamente essa estratégia são tecnicamente viáveis [cite: 3].
