    Terminal de Sistema em KaiOS Modificado: Otimização de Uso por Teclas Físicas, Aliases e Menus de Inicialização¶

    1. Visão geral¶

    Em aparelhos KaiOS com acesso a adb shell e privilégios de root, um terminal de sistema pode ser utilizado para investigação, diagnóstico e execução de comandos diretamente no dispositivo.

    Entretanto, aparelhos de baixo custo com teclado físico apresentam uma limitação prática importante: a entrada de comandos longos é lenta quando realizada exclusivamente pelas teclas alfanuméricas do aparelho.

    Uma solução não é substituir o terminal existente, mas criar uma camada de conveniência sobre ele. Essa camada pode utilizar:

    • Aliases;
    • Funções de shell;
    • Scripts de automação;
    • Menus interativos;
    • Comandos pré-programados;
    • Scripts de inicialização;
    • Atalhos para operações recorrentes.

    O objetivo é transformar operações que exigiriam vários caracteres em ações selecionáveis por poucas teclas.

    No contexto investigado neste manual, essa abordagem é particularmente relevante para o Multilaser Zapp II, cujo firmware apresenta:

    ro.build.version.release=4.4.2
ro.build.version.sdk=19
ro.product.version_tag=kaios_2_5_modric_20200721_20
ro.product.model=ZAPP_II
ro.board.platform=mt6572

    O kernel identificado é:

    Linux version 3.4.67

    Esses dados demonstram que o ambiente possui uma base Android antiga profundamente modificada para executar KaiOS. Portanto, comandos e comportamentos documentados para Android moderno não devem ser automaticamente considerados aplicáveis.

    2. Conceitos fundamentais¶

    2.1 Terminal existente versus terminal personalizado¶

    É importante distinguir duas abordagens:

    • Terminal personalizado: significa desenvolver uma nova interface ou aplicação de terminal.
    • Camada de conveniência: significa utilizar o terminal que já existe e adicionar mecanismos para facilitar sua utilização.

    Neste capítulo é adotada a segunda abordagem. A estrutura conceitual é:

    Teclas físicas
      │
      ▼
Terminal existente
      │
      ▼
Shell
      │
      ▼
Aliases / funções / scripts
      │
      ▼
Comandos do sistema

    O terminal continua responsável pela interface, o shell continua executando os comandos, e os scripts apenas reduzem a quantidade de entrada necessária.

    2.2 Alias¶

    Um alias associa uma palavra curta a um comando maior. Por exemplo:

    alias si='getprop ro.build.display.id'

    Depois disso, si pode executar o comando correspondente. Aliases são especialmente úteis para comandos:

    • Longos;
    • Executados frequentemente;
    • Difíceis de digitar;
    • Compostos por vários parâmetros.

    Porém, aliases normalmente são uma característica do shell e da sessão atual. Sua persistência depende de onde forem definidos.

    2.3 Funções de shell¶

    Funções são mais poderosas que aliases porque podem receber argumentos e executar várias operações. Exemplo:

    sysinfo() {
    getprop ro.product.model
    getprop ro.build.version.release
    getprop ro.build.display.id
}

    A função pode então ser executada simplesmente com:

    sysinfo

    Uma função é mais apropriada quando uma operação precisa combinar vários comandos.

    2.4 Scripts¶

    Um script é um arquivo contendo comandos executáveis pelo shell. Exemplo:

    #!/system/bin/sh

echo "Modelo:"
getprop ro.product.model

echo "Build:"
getprop ro.build.display.id

echo "KaiOS:"
getprop ro.product.version_tag

    Scripts são particularmente interessantes no Zapp II porque permitem criar ferramentas reutilizáveis sem modificar diretamente os componentes principais do sistema.

    2.5 Menu de inicialização¶

    Um menu pode funcionar como uma camada intermediária entre o usuário e o shell:

    ========================
     ZAPP II TOOLKIT
========================

1. Informações do sistema
2. Rede
3. Processos
4. Diagnóstico
5. Shell

Selecione:

    O usuário precisa digitar somente uma opção, em vez de conhecer e digitar o comando correspondente. Essa abordagem é especialmente adequada para aparelhos com teclado físico limitado.

    3. Como funciona¶

    Uma implementação simples pode seguir o seguinte fluxo:

    Terminal
   │
   ▼
Script inicial
   │
   ├── 1 → diagnóstico
   ├── 2 → rede
   ├── 3 → informações
   ├── 4 → ferramentas
   └── 5 → shell interativo

    O script pode utilizar case para selecionar uma operação:

    case "$opcao" in
    1)
        comando1
        ;;
    2)
        comando2
        ;;
    3)
        comando3
        ;;
esac

    Essa técnica utiliza recursos básicos do shell e, portanto, tende a ser mais compatível com ambientes embarcados do que depender de frameworks ou bibliotecas adicionais.

    3.1 Por que não substituir /system/bin/sh¶

    Modificar diretamente o shell do sistema é uma estratégia desnecessariamente invasiva. Por exemplo, substituir ou encapsular /system/bin/sh pode afetar:

    • Scripts de inicialização ;
    • Serviços ;
    • Comandos executados por outros processos ;
    • Scripts do firmware ;
    • Mecanismos de recuperação ;
    • Processos do próprio KaiOS.

    Portanto, não é recomendável modificar /system/bin/sh apenas para criar um menu. É preferível criar um executável ou script separado e configurar o terminal, quando isso for possível, para iniciar esse script.

    4. Componentes envolvidos¶

    Componente Função
    Terminal webapp Interface utilizada pelo usuário
    Shell Interpretador dos comandos
    /system/bin/sh Shell disponibilizado pelo firmware
    Scripts .sh Automação de operações
    Aliases Atalhos para comandos
    Funções shell Atalhos parametrizáveis
    getprop Consulta de propriedades do Android/KaiOS
    setprop Alteração de propriedades, quando permitido
    adb shell Acesso remoto ao shell
    su Obtenção de privilégios elevados, quando disponível

    A disponibilidade exata desses componentes deve ser verificada no firmware.

    5. Procedimentos práticos¶

    5.1 Verificar qual shell está sendo utilizado¶

    • Objetivo: Determinar qual interpretador está sendo executado antes de criar scripts dependentes de características específicas.

    Comando:

    adb shell 'echo $SHELL'

    Também pode ser útil:

    adb shell 'ls -l /system/bin/sh'

    Resultado esperado: O segundo comando deve mostrar o arquivo ou link utilizado como shell. No ambiente investigado, o shell é fornecido pelo próprio firmware. Não se deve assumir que seja equivalente a Bash.

    Diagnóstico: Verifique:

    adb shell 'sh --help'

    Caso --help não seja suportado, isso não significa necessariamente que o shell esteja com defeito. Shells embarcados frequentemente possuem conjuntos de opções reduzidos.

    5.2 Criar um primeiro script de diagnóstico¶

    • Objetivo: Criar uma ferramenta simples que concentre informações frequentemente utilizadas durante a investigação.
    • Pré-requisitos: Acesso ao terminal, permissão de execução e um diretório onde scripts possam ser armazenados.

    Um local temporário comum para testes é /data/local/tmp/.

    Criar o script:

    cat > /data/local/tmp/sysinfo.sh <<'EOF'
#!/system/bin/sh

echo "=== SISTEMA ==="
getprop ro.product.model
getprop ro.product.manufacturer
getprop ro.build.version.release
getprop ro.build.version.sdk

echo
echo "=== BUILD ==="
getprop ro.build.display.id
getprop ro.build.id
getprop ro.build.fingerprint

echo
echo "=== KAIOS ==="
getprop ro.product.version_tag

echo
echo "=== KERNEL ==="
uname -a
EOF

    Depois:

    chmod 755 /data/local/tmp/sysinfo.sh

    Executar:

    /data/local/tmp/sysinfo.sh

    Resultado esperado: O script deve produzir um resumo das propriedades principais do sistema.

    Como desfazer:

    rm /data/local/tmp/sysinfo.sh

    Esse procedimento não modifica a ROM. O arquivo criado pode ser removido posteriormente.

    5.3 Criar aliases¶

    • Objetivo: Reduzir comandos frequentemente utilizados durante a investigação.

    Exemplo:

    alias build='getprop ro.build.display.id'
alias kaios='getprop ro.product.version_tag'
alias kernel='uname -a'
alias model='getprop ro.product.model'

    Agora build, kaios, kernel e model podem substituir comandos mais longos.

    Limitação importante: O alias pode desaparecer quando a sessão do shell terminar. Para torná-lo persistente, é necessário identificar qual arquivo de inicialização o shell utilizado pelo firmware realmente lê. Não se deve presumir que /system/etc/profile ou /system/etc/mkshrc sejam utilizados sem verificar o comportamento do firmware.

    5.4 Identificar arquivos de inicialização do shell¶

    Antes de modificar qualquer arquivo, é preferível procurar referências ao shell. Exemplos:

    ls -la /system/etc/

    e:

    find /system/etc -maxdepth 2 -type f 2>/dev/null

    Dependendo das ferramentas disponíveis, pode-se procurar por arquivos conhecidos:

    find /system -name 'profile' 2>/dev/null

    ou:

    find /system -name '*shrc*' 2>/dev/null

    O resultado precisa ser analisado antes de qualquer alteração. A existência de um arquivo não prova que ele seja carregado pelo shell.

    5.5 Criar um menu interativo¶

    • Objetivo: Reduzir ainda mais a necessidade de digitação.

    Um exemplo minimalista:

    #!/system/bin/sh

while true
do
    clear

    echo "===================="
    echo "    ZAPP II TOOL"
    echo "===================="
    echo
    echo "1 - Sistema"
    echo "2 - Kernel"
    echo "3 - Rede"
    echo "4 - Shell"
    echo "5 - Sair"
    echo
    echo -n "Opcao: "

    read opcao

    case "$opcao" in
        1)
            getprop ro.product.model
            getprop ro.build.display.id
            getprop ro.product.version_tag
            echo
            echo "Pressione Enter..."
            read pausa
            ;;

        2)
            uname -a
            echo
            echo "Pressione Enter..."
            read pausa
            ;;

        3)
            ifconfig
            echo
            echo "Pressione Enter..."
            read pausa
            ;;

        4)
            exec /system/bin/sh
            ;;

        5)
            exit 0
            ;;

        *)
            echo "Opcao invalida."
            sleep 1
            ;;
    esac
done

    O uso de exec /system/bin/sh é conceitualmente importante. Em vez de iniciar outra camada desnecessária, o processo atual pode ser substituído por um shell. A disponibilidade de clear, sleep, ifconfig e outros comandos deve ser verificada no firmware específico.

    6. Exemplos¶

    6.1 Menu especializado em diagnóstico¶

    Em vez de criar um menu genérico, pode-se criar um menu voltado especificamente para o trabalho de engenharia do aparelho:

    ZAPP II DEBUG

1  Build
2  Kernel
3  Input
4  Bluetooth
5  USB
6  Processos
7  Shell
0  Sair

    Por exemplo, a opção 3 poderia executar cat /proc/bus/input/devices. Isso é particularmente útil porque esse arquivo permitiu verificar anteriormente os dispositivos de entrada presentes no Zapp II.

    6.2 Atalho para propriedades KaiOS¶

    Uma função:

    kaiosinfo() {
    echo "KaiOS:"
    getprop ro.product.version_tag

    echo "Build:"
    getprop ro.build.display.id

    echo "Android base:"
    getprop ro.build.version.release

    echo "SDK:"
    getprop ro.build.version.sdk
}

    Pode ser chamada com kaiosinfo. No firmware analisado, isso permite obter rapidamente:

    kaios_2_5_modric_20200721_20
4.4.2
19

    6.3 Atalhos para investigação de dispositivos de entrada¶

    Uma função útil durante investigação:

    inputs() {
    cat /proc/bus/input/devices
}

    Depois, basta executar inputs. Esse tipo de função é preferível a criar uma implementação própria de entrada, pois apenas encapsula uma ferramenta de diagnóstico já existente.

    7. Problemas comuns¶

    • Alias desaparece
      Causa provável: o alias foi criado somente na sessão atual.
      Solução: identificar o arquivo de inicialização efetivamente utilizado pelo shell.

    • read não funciona como esperado
      Algumas implementações de shell embarcado podem apresentar diferenças em relação ao Bash.
      Testar: bash read teste echo "$teste" Se houver comportamento inesperado, o script deve ser adaptado ao shell disponível.

    • clear não existe
      Verifique: which clear ou ls -l /system/bin/clear.
      Se não existir, o menu pode simplesmente não limpar a tela. Isso não impede o funcionamento do restante do script.

    • Script não executa
      Verifique: ls -l /data/local/tmp/script.sh e chmod 755 /data/local/tmp/script.sh.
      Também é possível executá-lo explicitamente: bash /system/bin/sh /data/local/tmp/script.sh Essa forma elimina a necessidade de o sistema reconhecer o shebang.

    • Comando existe no ADB, mas não no terminal
      Isso pode ocorrer por diferenças de PATH, usuário, permissões, ambiente, diretório atual ou shell utilizado pelo terminal.
      Compare echo "$PATH" no terminal e no ADB. Também é possível executar comandos usando caminhos absolutos quando conhecidos.

    8. Diagnóstico e debugging¶

    A primeira regra ao desenvolver ferramentas para esse ambiente é não modificar o sistema antes de entender seu comportamento.

    8.1 Verificar o ambiente¶

    id
whoami
echo "$PATH"
uname -a
getprop ro.build.display.id

    Esses comandos permitem registrar as condições sob as quais o script está sendo executado.

    8.2 Verificar comandos disponíveis¶

    Em vez de assumir que uma ferramenta existe:

    which comando

    ou:

    ls -l /system/bin/comando

    O firmware do Zapp II demonstrou anteriormente que alguns utilitários esperados em sistemas Linux completos não estão disponíveis (por exemplo, o comando file não estava instalado). Portanto, scripts destinados a esse aparelho devem evitar dependências desnecessárias.

    8.3 Registrar a saída¶

    Durante desenvolvimento, pode ser útil:

    /data/local/tmp/teste.sh > /data/local/tmp/teste.log 2>&1

    Isso permite preservar tanto a saída normal quanto os erros. Depois:

    cat /data/local/tmp/teste.log

    Esse método é especialmente útil quando o terminal apresenta limitações de visualização.

    8.4 Preservar evidências¶

    Durante engenharia reversa, não é recomendável editar diretamente arquivos importantes do sistema apenas para testar uma hipótese. É preferível:

    1. Copiar o arquivo ;
    2. Modificar a cópia ;
    3. Testar ;
    4. Registrar o resultado ;
    5. Somente então considerar uma alteração permanente.

    Por exemplo:

    cp arquivo_original arquivo_backup

    A localização e as permissões precisam ser verificadas antes de qualquer operação de cópia.

    9. Segurança e riscos¶

    Scripts de conveniência são relativamente seguros quando permanecem em áreas temporárias, mas o risco aumenta significativamente quando passam a modificar componentes do sistema.

    Baixo risco¶

    Exemplos em /data/local/tmp/. Scripts que apenas executam getprop, uname, cat e ls tendem a ser operações de leitura.

    Risco maior¶

    Alterações em /system/bin/, /system/etc/, /system/app/ e /system/framework/ podem causar consequências inesperadas. Particularmente perigoso é substituir /system/bin/sh ou modificar scripts de inicialização. Uma alteração incorreta pode impedir a inicialização de processos essenciais ou produzir um sistema parcialmente inutilizável.

    Regra prática: Para uma interface de conveniência, a arquitetura preferencial deve ser:

    ROM original
    │
    ├── Terminal existente
    │
    └── Script externo
           │
           ├── aliases
           ├── funções
           └── menu

    e não:

    ROM original
    ↓
substituição do shell
    ↓
modificação de componentes essenciais

    10. Compatibilidade¶

    A compatibilidade depende de diversos fatores:

    Fator Impacto
    Versão do KaiOS APIs e componentes podem mudar
    Base Android Define ferramentas e estrutura disponíveis
    Shell Determina sintaxe suportada
    Fabricante Pode remover comandos e modificar caminhos
    Chipset Afeta drivers e interfaces de hardware
    Terminal utilizado Determina como o shell é iniciado
    Root Determina quais operações podem ser executadas
    PATH Determina quais comandos podem ser chamados diretamente

    No Zapp II analisado, há evidências concretas de um ambiente bastante específico:

    • Android: 4.4.2
    • SDK: 19
    • Kernel: 3.4.67
    • SoC: MT6572
    • KaiOS tag: kaios_2_5_modric_20200721_20
    • Build: ML-SI04_ZAPP_II.V14_240730_1535

    Esses dados não devem ser generalizados para todos os aparelhos KaiOS. Além disso, a ausência de determinados comandos ou interfaces não significa necessariamente que o recurso correspondente não exista no sistema (por exemplo, /proc/config.gz não estava disponível no Zapp II, mas isso por si só não permite concluir quais opções foram utilizadas na compilação do kernel).

    11. Referências cruzadas¶

    Este capítulo está relacionado principalmente aos seguintes temas:

    • Arquitetura do KaiOS: necessário para compreender a relação entre Gecko, sistema embarcado e componentes derivados do Android.
    • ADB e acesso ao shell: necessário para acessar e testar scripts no dispositivo.
    • Root e permissões: necessário para operações que ultrapassam as permissões normais do usuário.
    • Debugging e diagnóstico: utiliza os mecanismos de coleta de informações apresentados neste capítulo.
    • Kernel e hardware: relevante quando scripts de diagnóstico consultam /proc, /sys e dispositivos de entrada.
    • Desenvolvimento de WebApps KaiOS: o terminal utilizado pelo usuário é uma aplicação, mas este capítulo trata apenas da camada de utilização do shell, não da implementação do WebApp.

    Um capítulo futuro sobre automação do ambiente de shell pode aprofundar persistência, inicialização automática, gerenciamento de scripts e criação de uma pequena suíte de ferramentas para o dispositivo.

    12. Resumo¶

    O uso de um terminal em um aparelho KaiOS com teclado físico limitado pode ser significativamente melhorado sem modificar o terminal ou desenvolver uma nova aplicação.

    As principais técnicas são:

    1. Aliases para comandos curtos e recorrentes.
    2. Funções de shell para operações compostas.
    3. Scripts para automatizar procedimentos.
    4. Menus numéricos para reduzir a necessidade de digitação.
    5. Scripts de diagnóstico para concentrar comandos utilizados frequentemente.
    6. Execução através de caminhos absolutos quando o PATH for inconsistente.
    7. Uso de /data/local/tmp/ durante desenvolvimento, reduzindo alterações permanentes no sistema.
    8. Preservação de evidências e backups antes de modificar componentes importantes.
    9. Evitar alterações em /system/bin/sh quando uma solução externa for suficiente.

    Para o Zapp II, a abordagem mais segura e prática é construir progressivamente uma pequena suíte de ferramentas de shell, começando por scripts de diagnóstico e menus simples e somente posteriormente avaliando mecanismos de inicialização automática.

    Integração com o restante do manual¶

    Depende de: Arquitetura do KaiOS, ADB e modos de depuração, Shell e permissões do sistema, Root, Estrutura do sistema de arquivos, Kernel Linux e interfaces /proc e /sys.

    Pode servir de base para: Automação do Zapp II, Ferramentas de diagnóstico, Engenharia reversa do firmware, Desenvolvimento de utilitários para KaiOS, Criação de uma suíte de manutenção do dispositivo, Investigação de hardware por linha de comando.

    Informações que devem ser verificadas na compilação final: Qual shell é efetivamente utilizado pelo terminal do Zapp II, quais arquivos de inicialização esse shell carrega, quais comandos estão realmente presentes no firmware, se o terminal permite configurar um comando ou script inicial, quais mecanismos de persistência são apropriados para o firmware específico, diferenças entre o firmware ML-SI04_ZAPP_II.V14 e outras versões do Zapp II.
