# Ferramentas Unix estáticas no KaiOS

## 1. Visão geral

Um dispositivo KaiOS com acesso root e ADB pode ser utilizado como ambiente de investigação e administração de baixo nível, permitindo executar ferramentas adicionais diretamente no aparelho.

Uma fonte interessante para esse propósito é o repositório **static-binaries**, de Ryan Woodsmall. O projeto disponibiliza diversos programas Linux compilados estaticamente com toolchains baseadas em **musl**, incluindo versões para `armhf`. O próprio projeto, porém, alerta que os binários podem não estar atualizados, que nem todas as arquiteturas possuem exatamente o mesmo conjunto de programas e que eles não devem ser utilizados para substituir integralmente o userspace do sistema.

No contexto desta seção, o objetivo não é transformar o KaiOS em uma distribuição Linux, mas disponibilizar **ferramentas portáteis para investigação, edição, diagnóstico, rede e manipulação de arquivos**.

Um ponto importante precisa ser corrigido em relação a uma suposição comum: `armeabi-v7a` **não significa automaticamente que qualquer binário chamado** `armhf`** será compatível**.

O Android define `armeabi-v7a` utilizando a convenção de chamadas `softfp`, enquanto o antigo `armeabi-v7a-hard` utilizava convenções de chamada hard-float. O Android atualmente documenta que `armeabi-v7a` usa `-mfloat-abi=softfp`; a própria documentação do NDK afirma que a variante `armeabi-v7a-hard` deixou de ser suportada.

Portanto:

> **ARMv7 é uma característica do processador.** `armhf` **é uma característica da ABI. As duas coisas não são sinônimas.**

A compatibilidade do binário precisa ser **testada no próprio dispositivo**.

---

## 2. Conceitos fundamentais

### 2.1 Arquitetura ARM

O Zapp II utilizado neste projeto reporta:

```
armeabi-v7a
```

Isso indica um ambiente ARM de 32 bits compatível com ARMv7. A documentação do Android descreve `armeabi-v7a` como ABI para CPUs ARM de 32 bits, incluindo Thumb-2 e Neon.

Isso responde à pergunta:

> "O processador consegue executar instruções ARMv7?"

Mas não responde sozinho:

> "Este binário específico pode ser executado pelo userspace deste sistema?"

Essa segunda pergunta envolve a ABI, o formato ELF, a biblioteca C, o carregador e as interfaces do kernel.

---

### 2.2 ABI

ABI, ou Application Binary Interface, define aspectos como:

- convenções de chamada;

- passagem de argumentos;

- retorno de valores;

- alinhamento;

- tamanho e representação de determinados tipos;

- interação entre código compilado e bibliotecas.

No caso do Android `armeabi-v7a`, a convenção de chamada utiliza `softfp`. Isso **não significa que o processador não tenha hardware de ponto flutuante**. O processador pode utilizar instruções de ponto flutuante por hardware, enquanto os argumentos das funções seguem a convenção `softfp`.

---

### 2.3 `armhf`

O termo `armhf` normalmente é utilizado para designar uma variante ARM com ABI hard-float.

Consequentemente, não é correto utilizar:

```
armeabi-v7a = armhf
```

como regra geral.

No caso dos binários do `static-binaries`, existe uma informação adicional importante: o projeto afirma que seus binários são construídos utilizando **musl-cross-make** e são estáticos.

Isso reduz algumas dependências de userspace, mas **não elimina incompatibilidades de ABI ou diferenças entre ambientes Linux**.

---

### 2.4 Binário estático

Um programa Linux convencional pode depender de bibliotecas externas:

```
programa
 |
 +-- libc
 +-- libm
 +-- libssl
 +-- outras bibliotecas
```

Um binário estático incorpora as bibliotecas necessárias ao próprio executável, dentro dos limites das bibliotecas utilizadas durante sua compilação.

A arquitetura fica mais próxima de:

```
programa
 |
 +-- código do programa
 +-- libc incorporada
 +-- outras bibliotecas incorporadas
 |
 v
kernel
```

Isso é particularmente interessante em sistemas embarcados porque reduz a dependência das bibliotecas existentes no aparelho.

Entretanto, **estático não significa universalmente compatível**.

O programa ainda depende do kernel e de recursos disponíveis no ambiente.

## 3. Como funciona

O fluxo recomendado para introduzir uma ferramenta no Zapp II é:

```
PC
 |
 | adb push
 v
/data/local/tmp/
 |
 | chmod
 v
executável
 |
 | execução
 v
kernel + filesystem + permissões
```

A primeira etapa deve ser sempre experimental.

Não é necessário instalar imediatamente o programa em um diretório permanente do sistema.

### Diretório de teste

O diretório:

```
/data/local/tmp/
```

é adequado para experimentação porque permite testar ferramentas sem modificar imediatamente os arquivos permanentes do sistema.

Exemplo:

```
adb push neatvi /data/local/tmp/neatvi
adb shell chmod 755 /data/local/tmp/neatvi
adb shell /data/local/tmp/neatvi
```

O resultado esperado é a inicialização do `neatvi`, caso o binário seja compatível com o ambiente.

## 5. Procedimentos práticos

## 5.1 Verificar a arquitetura informada pelo sistema

### Objetivo

Confirmar a ABI reportada pelo aparelho antes de testar binários.

### Comando

No computador:

```
adb shell getprop ro.product.cpu.abi
```

No Zapp II utilizado neste projeto, o resultado conhecido é:

```
armeabi-v7a
```

### Resultado esperado

```
armeabi-v7a
```

### Limitação

Esse resultado confirma a ABI declarada pelo sistema Android/KaiOS, mas **não comprova que um determinado binário** `armhf`** será executado**.

---

## 5.2 Inspecionar o binário antes de executá-lo

No computador Linux, uma ferramenta útil é:

```
file neatvi
```

Pode-se também examinar o ELF:

```
readelf -h neatvi
```

E procurar informações relacionadas à arquitetura:

```
readelf -A neatvi
```

Essas verificações permitem identificar características do executável antes de colocá-lo no telefone.

### Por que isso é importante?

Evita a situação:

```
baixar
 ↓
copiar para o telefone
 ↓
executar
 ↓
"não funciona"
```

e substitui por:

```
baixar
 ↓
inspecionar ELF
 ↓
identificar arquitetura/ABI
 ↓
copiar
 ↓
testar
```

---

## 5.3 Transferir `neatvi`

O projeto disponibiliza `neatvi` e descreve-o como um pequeno editor semelhante ao `vi`.

Depois de obter uma versão apropriada:

```
adb push neatvi /data/local/tmp/neatvi
```

Em seguida:

```
adb shell chmod 755 /data/local/tmp/neatvi
```

Teste:

```
adb shell /data/local/tmp/neatvi
```

Para abrir um arquivo:

```
adb shell /data/local/tmp/neatvi /caminho/para/arquivo
```

O caminho efetivamente utilizável depende do filesystem exposto pelo firmware.

---

## 5.4 Testar sem alterar o sistema

A recomendação é manter inicialmente as ferramentas em:

```
/data/local/tmp/
```

Por exemplo:

```
adb push neatvi /data/local/tmp/
adb shell chmod 755 /data/local/tmp/neatvi
adb shell /data/local/tmp/neatvi --help
```

Caso o programa não possua `--help`, isso não significa necessariamente que esteja quebrado. Alguns programas Unix simplesmente não implementam essa opção.

No caso do `neatvi`, o teste mais apropriado é simplesmente executá-lo em um arquivo de teste.

---

## 5.5 Criar um arquivo de teste

```
adb shell 'echo "Teste do neatvi no KaiOS" > /data/local/tmp/teste.txt'
```

Depois:

```
adb shell /data/local/tmp/neatvi /data/local/tmp/teste.txt
```

Após sair do editor:

```
adb shell cat /data/local/tmp/teste.txt
```

Isso fornece um teste simples do ciclo:

```
ADB
 ↓
filesystem
 ↓
neatvi
 ↓
edição
 ↓
gravação
 ↓
leitura
```

---

## 6.2 Por que `neatvi` é particularmente interessante

O `neatvi` possui uma função diferente de ferramentas como `busybox`.

O BusyBox fornece vários utilitários:

```
ls
cp
mv
cat
grep
sed
sh
...
```

Já o `neatvi` fornece um editor de texto.

Isso é útil porque, depois de obter shell root, torna-se possível investigar e editar arquivos diretamente no aparelho:

```
adb shell
```

e posteriormente:

```
/data/local/tmp/neatvi /algum/arquivo
```

Sem depender necessariamente de:

```
PC → editar → adb push → aparelho
```

para cada pequena alteração.

## 7. Problemas comuns

## 7.1 `Permission denied`

Exemplo:

```
Permission denied
```

Causa provável:

O arquivo não possui permissão de execução.

Verifique:

```
adb shell ls -l /data/local/tmp/neatvi
```

Corrija:

```
adb shell chmod 755 /data/local/tmp/neatvi
```

---

## 7.2 `No such file or directory`

Esse erro é particularmente enganoso.

Ele pode significar que o arquivo realmente não existe, mas também pode ocorrer quando o executável depende de um carregador ELF que não está disponível.

Verifique primeiro:

```
adb shell ls -l /data/local/tmp/neatvi
```

Depois:

```
adb shell /data/local/tmp/neatvi
```

Se o arquivo existir e ainda assim o sistema informar `No such file or directory`, deve-se investigar o ELF e suas dependências.

---

## 7.3 `Exec format error`

Exemplo:

```
Exec format error
```

Isso normalmente indica incompatibilidade do formato executável com a arquitetura ou ABI disponível.

Verifique no computador:

```
file neatvi
```

E:

```
readelf -h neatvi
```

Não se deve concluir simplesmente que:

```
armhf
```

é suficiente porque o telefone reporta:

```
armeabi-v7a
```

A distinção entre arquitetura e ABI é essencial nesse caso.

---

## 7.4 `Illegal instruction`

Exemplo:

```
Illegal instruction
```

O binário pode ter sido compilado utilizando instruções que o processador não suporta.

Isso é diferente de uma incompatibilidade simples de arquitetura.

Nesse caso, investigar:

```
cat /proc/cpuinfo
```

pode ajudar a identificar características do processador.

A disponibilidade efetiva de extensões ARM como NEON também pode variar. A documentação do Android observa que algumas extensões ARMv7 são opcionais e devem ser verificadas no dispositivo.

---

## 7.5 Erro 429 no GitHub

O erro:

```
429 Too Many Requests
```

é uma resposta de limitação de requisições do serviço.

Não é um erro de compatibilidade do binário.

Portanto:

```
HTTP 429
```

não significa:

```
neatvi incompatível
```

Significa que o download não foi obtido naquele momento.

Para a documentação do manual, deve-se manter essa distinção.

## 8. Diagnóstico e debugging

## 8.1 Confirmar o arquivo

```
adb shell ls -lh /data/local/tmp/neatvi
```

## 8.2 Confirmar permissões

```
adb shell ls -l /data/local/tmp/neatvi
```

O arquivo deve possuir bit de execução.

## 8.3 Confirmar arquitetura

No PC:

```
file neatvi
```

```
readelf -h neatvi
```

## 8.4 Confirmar arquitetura do dispositivo

```
adb shell getprop ro.product.cpu.abi
```

E, quando disponível:

```
adb shell cat /proc/cpuinfo
```

## 8.5 Observar mensagens do kernel

Com acesso adequado ao log:

```
adb shell dmesg
```

ou:

```
adb shell dmesg | tail
```

A disponibilidade e o nível de informação de `dmesg` dependem das permissões e da configuração do firmware.

---

## 8.6 Preservação de evidências

Durante investigação de KaiOS, é preferível inicialmente executar ferramentas a partir de:

```
/data/local/tmp/
```

em vez de modificar:

```
/system/
```

ou outras partições do firmware.

Isso mantém o experimento reversível:

```
copiar ferramenta
→ testar
→ apagar ferramenta
```

em vez de:

```
alterar userspace
→ modificar PATH
→ substituir binários
→ alterar permissões
→ descobrir incompatibilidade
```

Essa abordagem é especialmente importante em dispositivos com métodos de recuperação limitados.

## 9. Segurança e riscos

Ferramentas estáticas fornecem capacidades adicionais, mas não tornam o ambiente automaticamente seguro.

Com root, um comando incorreto pode modificar arquivos críticos.

### Evitar inicialmente

```
rm -rf
```

em diretórios do sistema.

Também deve-se evitar substituir binários existentes em:

```
/system/bin/
```

ou diretórios equivalentes sem backup e sem compreender o mecanismo de boot do firmware.

O próprio projeto `static-binaries` recomenda explicitamente não substituir o userspace existente por seus binários.

### Estratégia segura

Utilizar:

```
/data/local/tmp/
```

como área de laboratório.

Somente depois de comprovar:

1. arquitetura;

2. ABI;

3. funcionamento;

4. permissões;

5. dependências;

6. estabilidade;

deve-se considerar uma instalação permanente.

## 10. Compatibilidade

A compatibilidade precisa ser considerada em várias camadas.

| Camada | Pergunta |
| --- | --- |
| CPU | O processador executa ARMv7? |
| ABI | O binário utiliza uma ABI compatível? |
| ELF | O executável possui formato reconhecido? |
| libc | As funções necessárias estão incorporadas ou disponíveis? |
| Kernel | As syscalls necessárias existem? |
| Filesystem | Os caminhos e operações esperados existem? |
| Permissões | O processo possui os privilégios necessários? |
| Terminal | O programa consegue operar no terminal disponível? |
| KaiOS | O firmware impõe restrições adicionais? |

No caso do Zapp II:

No caso do Zapp II:

```
CPU/ABI reportada:
armeabi-v7a
```

Isso é uma evidência favorável para execução de software ARM de 32 bits, mas **não deve ser interpretado como confirmação automática de compatibilidade com** `armhf`.

A confirmação definitiva deve ser experimental.

## 12. Resumo

O acesso root e ADB permite utilizar o Zapp II como um pequeno ambiente de investigação de baixo nível.

O projeto `static-binaries` é uma fonte interessante porque disponibiliza diversos executáveis Linux construídos estaticamente com toolchains baseadas em musl, incluindo uma árvore `armhf`.

Entretanto, deve-se evitar a simplificação:

```
armeabi-v7a = armhf
```

O Zapp II reporta `armeabi-v7a`, enquanto `armhf` normalmente implica uma convenção ABI hard-float. O Android `armeabi-v7a` utiliza `softfp`, embora possa utilizar hardware de ponto flutuante internamente.

Assim, o procedimento correto é:

```
1. identificar a ABI do dispositivo
2. identificar a arquitetura do ELF
3. examinar o binário
4. copiar para /data/local/tmp/
5. atribuir permissão de execução
6. executar
7. analisar erros
8. somente então considerar instalação permanente
```

Para o ambiente de investigação do Zapp II, `neatvi`, `busybox`, `curl`, `jq`, `nc` e `xz` constituem um conjunto inicial particularmente útil. O `neatvi` é especialmente interessante por fornecer um editor de texto pequeno para uso diretamente no aparelho.
