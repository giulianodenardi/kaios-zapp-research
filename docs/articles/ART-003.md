# Binários nativos estáticos no KaiOS

## 1. Visão geral

O KaiOS utiliza uma base Linux embarcada, mas não deve ser tratado como uma distribuição Linux convencional. O sistema combina componentes do Linux/Gonk, serviços específicos do KaiOS, componentes do Android em determinadas gerações e o ambiente B2G/Gecko. A organização do sistema de arquivos, as permissões, o SELinux, a disponibilidade de bibliotecas e o acesso ao ADB variam conforme a versão, fabricante, chipset e firmware.

Uma possibilidade importante para análise, desenvolvimento e modificação de dispositivos KaiOS é executar **binários nativos compilados especificamente para a arquitetura do aparelho**.

Exemplos de ferramentas que podem ser utilizadas dessa forma incluem:

- `bash`
- `nano`
- `vim`
- `grep`
- `sed`
- `awk`
- `find`
- `tar`
- `gzip`
- pequenos utilitários próprios desenvolvidos em C

A principal vantagem de um binário estaticamente vinculado é reduzir a dependência de bibliotecas compartilhadas presentes no firmware. Entretanto, **"compilado estaticamente" não significa automaticamente "compatível com qualquer KaiOS"**. O executável ainda precisa ser compatível com a arquitetura do processador, com o formato ELF esperado, com o kernel e com as interfaces disponíveis.

Além disso, possuir um binário não significa possuir permissão para executá-lo em qualquer diretório. As permissões Unix e as políticas SELinux continuam sendo aplicadas.

O desenvolvimento oficial do KaiOS confirma a existência de acesso ADB em dispositivos de desenvolvimento/debug, mas a disponibilidade de `adb root` e o nível de privilégio obtido dependem do dispositivo.

---

## 2. Conceitos fundamentais

### 2.1 Binário nativo

Um binário nativo é um programa compilado para ser executado diretamente pelo processador do dispositivo.

Por exemplo, um programa C:

```
#include <stdio.h>

int main(void)
{
 printf("Hello KaiOS\n");
 return 0;
}
```

pode ser compilado para produzir um executável ELF.

O arquivo resultante não é um aplicativo KaiOS no sentido tradicional. Ele é um programa nativo destinado ao ambiente Linux subjacente.

Isso é diferente de uma aplicação Web/HTML instalada pelo mecanismo normal do KaiOS.

---

### 2.2 Binário dinamicamente vinculado

Um executável dinamicamente vinculado depende de bibliotecas compartilhadas existentes no sistema.

Um exemplo conceitual seria:

```
meu-programa
 |
 +-- libc.so
 +-- libm.so
 +-- outras bibliotecas
```

Se uma biblioteca necessária não existir, estiver em uma versão incompatível ou não estiver disponível no caminho esperado pelo carregador ELF, o programa pode não iniciar.

Um erro típico pode ser semelhante a:

```
CANNOT LINK EXECUTABLE
```

ou:

```
not found
```

dependendo do carregador e da versão do sistema.

---

### 2.3 Binário estaticamente vinculado

No vínculo estático, parte significativa das bibliotecas necessárias é incorporada ao próprio executável.

Conceitualmente:

```
programa estático
 |
 +-- código do programa
 +-- código necessário da libc
 +-- outras dependências vinculadas
```

Isso torna o binário muito mais independente do userland instalado no aparelho.

Porém, existem limitações. O programa ainda utiliza interfaces fornecidas pelo kernel e pode depender de mecanismos externos, como `/proc`, `/sys`, dispositivos, arquivos de configuração ou determinados recursos do sistema.

Portanto:

> Binário estático reduz dependências de bibliotecas. Não elimina dependências do sistema operacional.

---

### 2.4 Arquitetura do processador

Antes de compilar qualquer programa, é necessário descobrir a arquitetura do aparelho.

Uma maneira prática, quando o ADB está disponível, é consultar propriedades do sistema:

```
adb shell getprop ro.product.cpu.abi
```

Também pode ser útil:

```
adb shell getprop ro.product.cpu.abilist
```

e:

```
adb shell uname -m
```

Os resultados devem ser registrados antes da compilação.

Um aparelho ARM de 32 bits, por exemplo, não deve receber simplesmente um executável x86-64 compilado para um computador Linux convencional.

---

### 2.5 A arquitetura não é suficiente

Mesmo quando dois dispositivos utilizam ARM, isso não garante compatibilidade.

É necessário considerar:

| Característica | Exemplo de problema |
| --- | --- |
| Arquitetura | ARM vs ARM64 |
| ABI | ABI incompatível |
| Endianness | Normalmente little-endian, mas deve ser confirmado |
| libc | Bionic, musl, glibc ou outra implementação |
| Kernel | Recursos e interfaces diferentes |
| SELinux | Execução pode ser bloqueada |
| Diretório | Filesystem pode possuir restrições |
| Permissões | Arquivo pode não ter bit de execução |
| Firmware | Fabricante pode modificar componentes |

No ecossistema KaiOS, componentes Android/Bionic são particularmente relevantes em determinadas gerações. Portanto, utilizar um binário estático produzido em uma distribuição Linux convencional não garante compatibilidade simplesmente porque a arquitetura coincide.

## 3. Como funciona

O processo completo pode ser dividido em seis etapas:

```
┌──────────────────────┐
│ Identificar aparelho│
└──────────┬───────────┘
 ↓
┌──────────────────────┐
│ Identificar ABI/CPU │
└──────────┬───────────┘
 ↓
┌──────────────────────┐
│ Compilar o programa │
└──────────┬───────────┘
 ↓
┌──────────────────────┐
│ Transferir via ADB │
└──────────┬───────────┘
 ↓
┌──────────────────────┐
│ Ajustar permissões │
└──────────┬───────────┘
 ↓
┌──────────────────────┐
│ Executar/testar │
└──────────────────────┘
```

A primeira etapa deve sempre ser a identificação do dispositivo.

Não é recomendável começar copiando um binário para `/system/bin` simplesmente porque esse diretório contém outros executáveis.

## 4. Componentes envolvidos

### 4.1 ADB

O Android Debug Bridge é frequentemente utilizado para comunicação com dispositivos KaiOS que possuem o modo de depuração apropriado.

A documentação oficial do KaiOS apresenta o uso de:

```bash
adb devices
```

para verificar a conexão com o dispositivo.

Quando suportado pelo firmware, também pode existir:

```bash
adb root
```

Entretanto, `adb root` **não deve ser considerado universalmente disponível**. Dispositivos de produção podem impedir a execução do `adbd` como root.

### 4.2 Shell remoto

Com ADB funcionando:

```bash
adb shell
```

abre um shell no dispositivo.

Também é possível executar comandos diretamente:

```bash
adb shell uname -m
```

ou:

```bash
adb shell getprop ro.product.cpu.abi
```

### 4.3 Diretórios graváveis

Para testes, deve-se preferir inicialmente um diretório destinado a arquivos temporários ou dados graváveis.

Um exemplo comum é:

```text
/data/local/tmp/
```

Sua disponibilidade e permissões devem ser verificadas no próprio aparelho:

```bash
adb shell ls -ld /data/local/tmp
```

Não se deve presumir que um determinado diretório será gravável em todos os modelos.

### 4.4 `/system/bin`

Em dispositivos KaiOS baseados em componentes Android/Gonk, `/system/bin` pode conter executáveis nativos do sistema.

Entretanto, isso **não significa que o usuário possa modificar esse diretório**.

Em muitos aparelhos:

```text
/system
```

é montado como somente leitura.

Além disso, mesmo que seja possível obter privilégios suficientes para modificar a partição, o SELinux, o sistema de montagem, a proteção do firmware ou mecanismos de integridade podem impedir a operação.

## 5. Procedimentos práticos

### 5.1 Procedimento A: identificar a arquitetura

#### Objetivo

Descobrir para qual arquitetura e ABI o binário deverá ser compilado.

#### Pré-requisitos

- ADB funcionando;
- aparelho em modo de depuração;
- computador com `adb`.

#### Comandos

```
adb devices
```

Depois:

```
adb shell getprop ro.product.cpu.abi
adb shell getprop ro.product.cpu.abilist
adb shell uname -m
```

Também é possível consultar:

```
adb shell getprop ro.build.version.release
```

e:

```
adb shell getprop ro.build.version.sdk
```

#### Resultado esperado

O objetivo é obter informações semelhantes a:

```
armeabi-v7a
```

ou:

```
arm64-v8a
```

e uma identificação correspondente do kernel.

Os valores exatos dependem do aparelho.

#### Possíveis erros

Se aparecer:

```
adb: no devices/emulators found
```

o problema ainda não está relacionado ao binário. Primeiro é necessário resolver a conexão ADB.

Se o dispositivo aparecer como:

```
unauthorized
```

é necessário investigar a autorização/debug do aparelho. A própria comunidade KaiOS documenta que determinados dispositivos comerciais não possuem chaves ADB apropriadas e podem apresentar esse estado.

---

### 5.2 Procedimento B: verificar o ambiente nativo

Antes de instalar um programa grande, deve-se descobrir quais ferramentas já existem.

Por exemplo:

```
adb shell ls -l /system/bin
```

Para procurar BusyBox:

```
adb shell ls -l /system/bin/busybox
```

Se o arquivo existir:

```
adb shell /system/bin/busybox
```

poderá mostrar os applets disponíveis.

A presença de BusyBox não deve ser presumida. Há aparelhos KaiOS que possuem o programa e outros que não o possuem. Registros da comunidade mostram o uso de `/system/bin/busybox` em determinados dispositivos KaiOS, mas isso não constitui uma característica universal da plataforma.

---

### 5.3 Procedimento C: transferir um binário

Supondo que exista um executável chamado:

```
hello
```

no computador:

```
adb push hello /data/local/tmp/hello
```

Depois:

```
adb shell chmod 755 /data/local/tmp/hello
```

E então:

```
adb shell /data/local/tmp/hello
```

#### Resultado esperado

O programa deve iniciar e produzir sua saída normal.

Por exemplo:

```
Hello KaiOS
```

#### Diagnóstico

Se ocorrer:

```
Permission denied
```

verifique:

```
adb shell ls -l /data/local/tmp/hello
```

O resultado deverá indicar o bit de execução, por exemplo:

```
-rwxr-xr-x
```

Se o arquivo possuir permissão de execução e ainda assim falhar, o problema pode estar relacionado ao SELinux ou a outras restrições do ambiente.

---

### 5.4 Procedimento D: verificar se o executável é realmente estático

No computador Linux, pode-se utilizar:

```
file hello
```

Para um executável estático, espera-se uma descrição indicando vínculo estático, quando suportado pela ferramenta `file`.

Também pode ser utilizado:

```
readelf -l hello
```

e:

```
readelf -d hello
```

Um executável ELF dinamicamente vinculado normalmente apresenta informações relacionadas ao carregador dinâmico e à seção de dependências.

A ausência de dependências dinâmicas é um indício importante, mas deve ser interpretada de acordo com a ferramenta e o formato do binário.

---

### 5.5 Procedimento E: testar primeiro em `/data/local/tmp`

A estratégia recomendada é:

```
compilar
 ↓
transferir
 ↓
executar em diretório temporário
 ↓
validar
 ↓
investigar dependências
 ↓
somente depois considerar instalação permanente
```

Exemplo:

```
adb push nano /data/local/tmp/nano
adb shell chmod 755 /data/local/tmp/nano
adb shell /data/local/tmp/nano
```

Essa abordagem evita modificar imediatamente a imagem do sistema.

## 6. Compilação

### 6.1 Compilação nativa

Se o ambiente de compilação possuir uma toolchain adequada à arquitetura do dispositivo, um programa simples pode ser compilado com:

```
gcc -static -o hello hello.c
```

Entretanto, esse comando **não deve ser interpretado como uma receita universal para KaiOS**.

Um `gcc` configurado para glibc em um PC Linux pode produzir um executável incompatível com o ambiente nativo do telefone, mesmo utilizando a arquitetura ARM correta.

---

### 6.2 Cross-compilação

Em muitos casos será necessário utilizar uma toolchain de cross-compilação.

Conceitualmente:

```
PC x86-64
 |
 | cross compiler
 ↓
ARM/ARM64 ELF
 |
 ↓
KaiOS
```

A toolchain precisa ser compatível com a ABI desejada.

Para projetos maiores, a forma mais confiável é utilizar uma toolchain ou SDK correspondente ao ambiente alvo, quando disponível.

---

### 6.3 O caso do Bash

O `bash` é um exemplo particularmente interessante.

Ele é muito maior e mais complexo que utilitários simples como:

```
cat
echo
true
false
pwd
```

Além disso, o Bash espera determinados comportamentos do ambiente Unix.

Mesmo que seja possível gerar um executável estático, algumas funcionalidades podem depender de:

- `/dev`;
- `/proc`;
- sinais;
- terminais;
- variáveis de ambiente;
- arquivos de configuração;
- permissões;
- comportamento específico do kernel.

Portanto, o primeiro objetivo deve ser obter:

```
bash --version
```

e posteriormente testar funcionalidades individualmente.

---

### 6.4 O caso do Nano

O `nano` também é um programa nativo, mas depende de uma interface de terminal funcional.

Em um ambiente ADB:

```
adb shell /data/local/tmp/nano arquivo.txt
```

pode não proporcionar a mesma experiência de um terminal Linux convencional.

Isso ocorre porque o problema pode não estar no `nano`, mas na forma como o shell ADB fornece o terminal, no suporte a `PTY`, no teclado e na configuração do terminal.

Portanto, instalar `nano` não equivale automaticamente a possuir um ambiente de terminal completo.

---

## 7. Instalação permanente

Existem três conceitos diferentes que não devem ser confundidos:

1. **executar temporariamente
um binário;**
2. **armazenar
permanentemente um binário em uma área gravável;**
3. **integrar o binário à
imagem do sistema.**

A primeira opção é a mais simples.

A segunda depende das permissões e do layout do dispositivo.

A terceira é uma modificação de firmware e deve ser tratada em um capítulo próprio.

---

### 7.1 Armazenamento persistente

Se existir um diretório apropriado e gravável:

```
adb shell mkdir -p /data/local/bin
```

pode ser possível armazenar ferramentas ali.

Depois:

```
adb push bash /data/local/bin/bash
```

e:

```
adb shell chmod 755 /data/local/bin/bash
```

Porém, a existência e persistência de `/data/local/bin` não devem ser consideradas garantidas em todos os aparelhos.

O ponto importante é que o diretório deve ser validado no dispositivo antes de ser utilizado.

---

### 7.2 Modificar `/system/bin`

A abordagem:

```
cp programa /system/bin/
```

não deve ser utilizada como primeiro procedimento.

Ela depende de:

- acesso privilegiado;
- `/system` montável como leitura/escrita;
- permissões adequadas;
- política SELinux;
- estrutura de partições;
- mecanismos de proteção do firmware.

Além disso, modificar arquivos existentes em `/system/bin` pode impedir o funcionamento normal do sistema.

A existência de acesso ADB não significa automaticamente capacidade de modificar `/system`.

---

## 8. Exemplos

### 8.1 Programa mínimo

Um teste inicial muito melhor que `bash` ou `nano` é um programa extremamente simples.

```
#include <stdio.h>

int main(void)
{
 puts("KaiOS native test");
 return 0;
}
```

Compile-o para a arquitetura correta e transfira:

```
adb push hello /data/local/tmp/hello
adb shell chmod 755 /data/local/tmp/hello
adb shell /data/local/tmp/hello
```

Se funcionar, significa que o caminho básico:

```
ELF → arquitetura → kernel → permissões → execução
```

está operacional.

---

### 8.2 Programa para inspeção do ambiente

Um pequeno programa nativo pode também ser usado para identificar características do ambiente.

Por exemplo:

```
#include <stdio.h>
#include <unistd.h>

int main(void)
{
 printf("UID: %d\n", getuid());
 printf("PID: %d\n", getpid());

 return 0;
}
```

Esse tipo de ferramenta é útil durante a investigação porque permite determinar com qual identidade o processo está sendo executado.

---

### 8.3 Ferramentas maiores

Depois de validar um programa mínimo, pode-se avançar gradualmente:

```
hello
 ↓
cat
 ↓
grep
 ↓
sed
 ↓
tar
 ↓
vim/nano
 ↓
bash
```

Essa progressão reduz a quantidade de variáveis durante o diagnóstico.

## 9. Problemas comuns

| Sintoma | Possível causa |
| --- | --- |
| `Permission denied` | Permissões Unix ou SELinux |
| `No such file or directory` | Caminho incorreto ou carregador ELF ausente |
| `CANNOT LINK EXECUTABLE` | Dependência dinâmica incompatível |
| Executável não inicia | Arquitetura/ABI incompatível |
| `adb push` falha | Diretório sem permissão ou ADB limitado |
| `adb root` falha | Firmware de produção ou `adbd` sem suporte a root |
| Programa funciona no PC e não no telefone | Toolchain/ABI incompatível |
| `nano` inicia mas terminal funciona mal | Limitações de PTY/terminal |
| Programa desaparece após reinicialização | Armazenamento temporário ou área não persistente |
| `/system` não pode ser modificado | Partição somente leitura, SELinux ou proteção do firmware |

## 10. Diagnóstico e debugging

O diagnóstico deve começar pelo nível mais baixo possível.

### 10.1 Identificar o arquivo

No computador:

```
file programa
```

Depois:

```
readelf -h programa
```

Esses comandos ajudam a identificar o formato ELF e a arquitetura indicada no executável.

---

### 10.2 Verificar permissões

No dispositivo:

```
adb shell ls -l /data/local/tmp/programa
```

---

### 10.3 Verificar arquitetura do dispositivo

```
adb shell uname -m
```

e:

```
adb shell getprop ro.product.cpu.abi
```

---

### 10.4 Verificar identidade do processo

```
adb shell id
```

Resultado semelhante a:

```
uid=0(root)
```

ou:

```
uid=2000(shell)
```

deve ser interpretado como evidência do nível de privilégio disponível naquele momento.

Não se deve presumir que todo acesso ADB seja root.

---

### 10.5 Verificar SELinux

Quando disponível:

```
adb shell getenforce
```

Um resultado como:

```
Enforcing
```

indica que a política SELinux está sendo aplicada.

O SELinux pode impedir uma operação mesmo quando as permissões Unix aparentam estar corretas.

Em versões recentes do KaiOS, o controle de acesso é especialmente relevante. Pesquisas recentes sobre KaiOS 3.1 documentam diferentes domínios SELinux, incluindo `B2G`, `Api-daemon` e `Shell`, mostrando que possuir execução de comandos não significa possuir acesso irrestrito ao sistema.

---

### 10.6 Preservação de evidências

Durante investigação, não se deve substituir imediatamente arquivos existentes.

Em vez de:

```
cp programa /system/bin/programa
```

prefira:

```
adb push programa /data/local/tmp/programa
```

e teste isoladamente.

Quando possível, registre:

```
adb shell uname -a
adb shell id
adb shell getenforce
adb shell getprop ro.product.cpu.abi
adb shell getprop ro.build.version.release
adb shell getprop ro.build.version.sdk
```

Essas informações ajudam a reproduzir posteriormente o ambiente.

---

## 11. Segurança e riscos

A instalação de binários nativos possui riscos significativamente maiores que a instalação de uma aplicação Web convencional.

### 11.1 Executar como root

Um programa executado como root pode modificar partes críticas do sistema.

Um erro simples em comandos como:

```
rm
chmod
chown
mount
cp
```

pode causar perda de dados ou tornar o sistema inutilizável.

---

### 11.2 Modificar `/system`

Modificar a partição do sistema pode:

- quebrar componentes do KaiOS;
- impedir a inicialização;
- interferir em atualizações;
- modificar permissões;
- gerar inconsistências no firmware.

Portanto, `/system` deve ser tratado como área de alto risco.

---

### 11.3 Binários desconhecidos

Um executável nativo possui acesso às mesmas interfaces do sistema disponíveis para o processo que o executa.

Não se deve copiar para um aparelho um binário de origem desconhecida e executá-lo com privilégios elevados.

---

### 11.4 SELinux

Tentar contornar o SELinux apenas para fazer um programa funcionar pode produzir resultados difíceis de diagnosticar.

O ideal é primeiro descobrir **qual regra está impedindo a operação**.

---

### 11.5 Brick

A instalação de um executável em `/data/local/tmp` normalmente é muito menos arriscada que modificar partições de sistema.

A alteração de:

```
/system
/vendor
/boot
```

ou outras partições do firmware pertence ao nível de modificação de firmware e deve ser realizada somente depois que houver:

- backup;
- método de recuperação;
- identificação exata do firmware;
- documentação do particionamento;
- confirmação da compatibilidade.

---

## 12. Compatibilidade

A compatibilidade deve ser avaliada em várias dimensões.

| Fator | O que verificar |
| --- | --- |
| KaiOS | 2.5.x, 3.x etc. |
| Modelo | Aparelho específico |
| Fabricante | Implementação do OEM |
| Chipset | MediaTek, Qualcomm, Spreadtrum/Unisoc etc. |
| CPU | ARM32, ARM64 etc. |
| ABI | `armeabi-v7a`, `arm64-v8a` etc. |
| libc | Implementação utilizada pelo ambiente |
| Kernel | Versão e recursos disponíveis |
| SELinux | Modo e política |
| ADB | Disponível ou bloqueado |
| Privilégios | Shell, B2G, root etc. |
| Partições | Somente leitura ou leitura/escrita |
| Persistência | `/data`, `/system` e demais áreas |

As diferenças entre versões são especialmente importantes.

A documentação oficial ainda apresenta procedimentos diferentes para ambientes KaiOS tradicionais e KaiOS 3.x, inclusive diferenças na infraestrutura de desenvolvimento e ferramentas.

Consequentemente, um procedimento confirmado em um KaiOS 2.5 não deve ser automaticamente aplicado a um KaiOS 3.x.

## 14. Resumo

Binários nativos estáticos podem ser uma maneira eficiente de adicionar ferramentas Unix a um ambiente KaiOS limitado, principalmente durante desenvolvimento, debugging e pesquisa do sistema.

O procedimento recomendado é:

```
1. Identificar CPU e ABI
2. Identificar versão do KaiOS
3. Identificar ambiente e privilégios
4. Compilar para a arquitetura correta
5. Preferir vínculo estático quando apropriado
6. Transferir para uma área temporária
7. Aplicar chmod
8. Executar e testar
9. Diagnosticar permissões/SELinux
10. Somente depois considerar persistência
```

Um exemplo mínimo é:

```
adb push programa /data/local/tmp/programa
adb shell chmod 755 /data/local/tmp/programa
adb shell /data/local/tmp/programa
```

A estratégia mais segura é **não modificar** `/system`** durante os primeiros testes**.

Também é importante distinguir três objetivos diferentes:

```
Executar um binário
 ≠
Armazenar um binário permanentemente
 ≠
Integrar um binário ao firmware
```

Cada um desses níveis exige privilégios e procedimentos diferentes.
