# Ambiente Linux em chroot no Zapp II

## 1. Visão geral

O Zapp II utilizado neste projeto apresenta uma combinação particular de componentes de software baseados em Linux, Android e KaiOS. Para fins de engenharia e experimentação, é possível aproveitar o ambiente Linux já existente no aparelho para criar um *root filesystem* (*rootfs*) independente, executado por meio de `chroot`.

O objetivo deste ambiente não é substituir o sistema operacional principal, mas fornecer um espaço Linux adicional dentro do sistema existente.

Nesse modelo:

```text
┌──────────────────────────────────────────────┐
│ Zapp II                                      │
│                                              │
│ ┌──────────────────────────────────────────┐ │
│ │ Sistema principal                        │ │
│ │ Linux / Android / KaiOS                  │ │
│ │                                          │ │
│ │ /system                                  │ │
│ │ /data                                    │ │
│ │ /vendor                                  │ │
│ │ /dev                                     │ │
│ │ /proc                                    │ │
│ │ /sys                                     │ │
│ └──────────────────────┬───────────────────┘ │
│                        │                     │
│                        │ chroot              │
│                        ▼                     │
│ ┌──────────────────────────────────────────┐ │
│ │ /data/local/linux                        │ │
│ │                                          │ │
│ │ /bin                                     │ │
│ │ /sbin                                    │ │
│ │ /usr                                     │ │
│ │ /etc                                     │ │
│ │ /root                                    │ │
│ │ /proc                                    │ │
│ │ /sys                                     │ │
│ │ /dev                                     │ │
│ └──────────────────────────────────────────┘ │
└──────────────────────────────────────────────┘
```

O ambiente criado neste projeto utiliza principalmente o BusyBox 1.21.1, compilado para ARMv7, como conjunto de ferramentas Unix.

O ambiente foi testado no Zapp II com:

| Componente | Evidência observada |
| :--- | :--- |
| **SoC** | MediaTek MT6572 |
| **Arquitetura** | ARMv7 |
| **KaiOS** | 2.5.1.2 |
| **Kernel** | Linux 3.4.67 |
| **BusyBox** | 1.21.1 |
| **BusyBox principal** | `/system/xbin/busybox` |
| **Root durante os testes** | `uid=0(root) gid=0(root)` |
| **Rootfs experimental** | `/data/local/linux` |
| **Sistema `/data`** | `ext4`, montado `rw` |
| **SELinux** | `Enforcing` |

> **Nota:** Essas informações são específicas do aparelho e firmware investigados e não devem ser generalizadas para todos os dispositivos KaiOS.

## 2. Conceitos fundamentais

### 2.1 Linux, Android, KaiOS e userland

É importante separar três conceitos diferentes:

1. **Kernel**
2. **Sistema operacional/runtime**
3. **Userland**

O kernel fornece funções fundamentais como:

* processos;
* memória;
* dispositivos;
* sistemas de arquivos;
* rede;
* drivers;
* permissões;
* chamadas de sistema.

O Android utiliza um kernel Linux, mas possui seu próprio conjunto de componentes e serviços. O KaiOS também utiliza tecnologias baseadas em Linux e possui uma camada de runtime própria. Portanto, dizer que *"Android e Linux userland são a mesma coisa"* não é tecnicamente correto.

Um sistema Android possui um userland Android, que pode incluir componentes como:

* `/system`
* `/vendor`
* `/data`
* `/bin`
* `/xbin`
* serviços Android
* bibliotecas
* framework
* runtime

O KaiOS acrescenta sua própria camada de software sobre a infraestrutura fornecida pelo dispositivo.

O `chroot` explorado neste projeto não cria um novo kernel. Ele reutiliza o kernel já executado pelo aparelho.

### 2.2 O que é chroot

`chroot` significa aproximadamente *"change root"*. O comando altera o diretório que será tratado como `/` para um processo e seus descendentes.

Por exemplo:

```bash
chroot /data/local/linux /bin/sh
```

Antes:

```text
/
├── system
├── data
├── vendor
└── ...
```

Depois, para o processo dentro do chroot:

```text
/
├── bin
├── etc
├── usr
├── root
└── ...
```

Nesse caso:

```text
/data/local/linux/bin/sh
```

passa a ser percebido pelo processo como:

```text
/bin/sh
```

Entretanto, `chroot` não é uma máquina virtual e não é um container completo. O processo continua utilizando:

* o mesmo kernel;
* os mesmos dispositivos subjacentes;
* a mesma arquitetura;
* os mesmos mecanismos de segurança do kernel;
* o mesmo namespace de processos, salvo outras técnicas adicionais;
* as mesmas limitações impostas pelo sistema hospedeiro.

### 2.3 Root filesystem

O diretório utilizado neste projeto foi:

```text
/data/local/linux
```

Esse diretório funciona como rootfs experimental. Uma estrutura mínima pode ser:

```text
/data/local/linux/
├── bin/
├── sbin/
├── usr/
│   ├── bin/
│   └── sbin/
├── etc/
├── dev/
├── proc/
├── sys/
├── tmp/
└── root/
```

O rootfs precisa conter os executáveis e bibliotecas necessários para executar o ambiente.

### 2.4 BusyBox

BusyBox é um executável que reúne diversas ferramentas Unix em um único binário.

No aparelho investigado:

```bash
which busybox
```

retornou:

```text
/system/xbin/busybox
```

A versão observada foi:

```text
BusyBox v1.21.1
```

O binário disponibiliza dezenas de applets, incluindo: `sh`, `ls`, `cat`, `mount`, `cp`, `mv`, `rm`, `chmod`, `chown`, `ps`, `ping`, `ifconfig`, `tar`, `wget`, `vi`, `su`, entre muitos outros.

Isso é particularmente útil em sistemas embarcados porque um único executável pode fornecer uma grande quantidade de ferramentas.

## 3. Como funciona

O funcionamento do ambiente pode ser dividido em quatro camadas:

```text
┌─────────────────────────────┐
│ Aplicações / shell          │
├─────────────────────────────┤
│ BusyBox / userland          │
├─────────────────────────────┤
│ Rootfs /data/local/linux    │
├─────────────────────────────┤
│ Kernel Linux do aparelho    │
└─────────────────────────────┘
```

O `chroot` altera a visão do sistema de arquivos para o processo. O BusyBox fornece as ferramentas. O kernel continua sendo o kernel do Zapp II.

Isso explica por que um programa executado no mini-Linux consegue utilizar a interface `wlan0` existente no aparelho.

### 3.1 Execução do shell

O ponto de entrada utilizado foi:

```bash
chroot /data/local/linux /bin/sh
```

Quando esse comando funciona, o prompt muda para algo semelhante a:

```text
/ #
```

Nesse momento, `/` representa `/data/local/linux` no sistema hospedeiro.

### 3.2 PATH

Dentro do chroot, o PATH inicialmente observado foi:

```text
/sbin:/vendor/bin:/system/sbin:/system/bin:/system/xbin
```

Foi então configurado:

```bash
export PATH=/bin:/sbin:/usr/bin:/usr/sbin
```

Isso é conceitualmente correto, mas não é suficiente por si só. O shell procura:

* `/bin/ls`
* `/sbin/mount`
* `/usr/bin/cat`
* `/usr/sbin/...`

Portanto, esses arquivos precisam realmente existir no rootfs e ser executáveis.

## 4. Componentes envolvidos

### 4.1 Sistema hospedeiro

Os principais componentes observados foram:

* `/system`
* `/data`
* `/vendor`
* `/dev`
* `/proc`
* `/sys`

O sistema `/system` foi observado inicialmente como:

```text
/emmc@android /system ext4 ro,seclabel,relatime,data=ordered 0 0
```

Durante os testes, foi possível remontá-lo como `rw`:

```bash
/system/xbin/busybox mount -o remount,rw /system
```

Posteriormente:

```text
/emmc@android /system ext4 rw,seclabel,relatime,data=ordered 0 0
```

> **Aviso:** Essa alteração deve ser tratada como operação potencialmente perigosa e não deve ser considerada necessária para um chroot convencional.

### 4.2 Rootfs

O rootfs experimental está localizado em:

```text
/data/local/linux
```

Os arquivos do BusyBox foram distribuídos nesse ambiente. Durante a montagem do ambiente, foi criado um conjunto de links para os applets.

Por exemplo:

* `/data/local/linux/bin/ls`
* `/data/local/linux/bin/mount`
* `/data/local/linux/bin/cat`

### 4.3 BusyBox

O executável principal é:

```text
/system/xbin/busybox
```

Foi confirmado:

```bash
/system/xbin/busybox --help
```

com resultado indicando `BusyBox v1.21.1`.

O BusyBox também contém o applet `su`. Entretanto, a simples presença do applet `su` não significa que ele esteja configurado como um mecanismo funcional de escalada de privilégios.

## 5. Procedimentos práticos

### 5.1 Verificar o BusyBox do sistema

* **Objetivo:** Confirmar a localização e a versão do BusyBox.
* **Comandos:**

```bash
which busybox
/system/xbin/busybox --help
```

* **Resultado observado:** `/system/xbin/busybox` e `BusyBox v1.21.1`.
* **Diagnóstico:** Caso `which` não encontre o executável, utilizar diretamente `/system/xbin/busybox`.

### 5.2 Criar ou verificar o rootfs

* **Objetivo:** Confirmar a existência do ambiente Linux.

```bash
ls -l /data/local/linux
```

Uma estrutura mínima esperada inclui: `bin`, `etc`, `root`, `usr`, `tmp`, `dev`, `proc`, `sys`.

### 5.3 Entrar no mini-Linux

* **Comando:**

```bash
chroot /data/local/linux /bin/sh
```

* **Resultado esperado:** `/ #`
* **Diagnóstico:** Se ocorrer `chroot: can't execute '/bin/sh': No such file or directory`, não significa necessariamente que `/bin/sh` não exista. Possíveis causas incluem:
  * arquivo ausente;
  * link simbólico quebrado;
  * arquitetura incompatível;
  * biblioteca dinâmica ausente;
  * interpretador ELF ausente.

Nesse caso, deve-se investigar o executável antes de substituí-lo.

### 5.4 Configurar o PATH

Dentro do ambiente:

```bash
export PATH=/bin:/sbin:/usr/bin:/usr/sbin
```

Verificar:

```bash
echo $PATH
```

* **Resultado esperado:** `/bin:/sbin:/usr/bin:/usr/sbin`

> Isso apenas informa ao shell onde procurar executáveis. Não cria os executáveis.

### 5.5 Instalar applets do BusyBox no rootfs

O BusyBox possui `busybox --install` e `busybox --install -s`. A opção `-s` solicita links simbólicos em vez de cópias.

No rootfs, a operação deve ser direcionada explicitamente ao diretório desejado:

```bash
/system/xbin/busybox --install -s /data/local/linux/bin
```

ou, se o BusyBox estiver disponível dentro do rootfs:

```bash
/bin/busybox --install -s /bin
```

> **Observação importante:** Não é recomendável executar simplesmente `busybox --install -s` sem especificar o destino durante a preparação de um rootfs. No teste realizado anteriormente, isso fez o BusyBox tentar criar applets em caminhos do sistema hospedeiro, como `/bin`, `/sbin`, `/usr/bin`, `/usr/sbin`, produzindo mensagens como `Read-only file system` e `No such file or directory`. Portanto, o problema não era ausência dos applets no BusyBox, mas sim o destino utilizado pelo `--install`.

### 5.6 Problema dos links absolutos

Durante os testes foi observado:

```bash
ls -l /data/local/linux/bin/ls
```

resultando em:

```text
ls -> /system/xbin/busybox
```

Esse detalhe é fundamental. Dentro do chroot, o processo interpreta `/system/xbin/busybox` como um caminho pertencente ao rootfs (`/data/local/linux/system/xbin/busybox`) e não necessariamente como o `/system/xbin/busybox` do sistema hospedeiro.

Por isso, um link como `/bin/ls -> /system/xbin/busybox` pode parecer correto fora do chroot, mas falhar dentro dele.

A solução correta é disponibilizar o BusyBox dentro do rootfs e criar links que apontem para uma localização válida dentro desse mesmo rootfs. Por exemplo:

* `/bin/busybox`
* `/bin/ls -> busybox`
* `/bin/cat -> busybox`
* `/bin/mount -> busybox`

ou utilizar links absolutos que apontem para uma localização existente dentro do rootfs.

### 5.7 Testar a rede

A rede foi efetivamente demonstrada dentro do chroot.

* **Comando utilizado:**

```bash
/bin/busybox ifconfig
```

Foi possível observar `lo` e `wlan0`, com `wlan0` apresentando `inet addr:192.168.0.16`.

Também foi observado:

```text
ifconfig: /proc/net/dev: No such file or directory
```

Esse aviso indica que `/proc` não estava corretamente disponível no ambiente naquele momento. Apesar disso, as interfaces de rede puderam ser identificadas.

### 5.8 Testar conectividade IP

Foi executado:

```bash
/bin/busybox ping -c 3 8.8.8.8
```

* **Resultado:**

```text
3 packets transmitted, 3 packets received, 0% packet loss
```

com latência média aproximada de `28.957 ms`.

Isso demonstra que o processo executado dentro do chroot conseguiu utilizar a conectividade de rede do sistema hospedeiro.

> **Conclusão:** O chroot não possui uma pilha de rede independente. Ele utiliza a infraestrutura de rede fornecida pelo kernel e pelo ambiente hospedeiro.

### 5.9 Disponibilizar /proc

Ferramentas como `ps`, `ifconfig`, `free` e `top` podem depender de informações fornecidas por `/proc`. O erro `/proc/net/dev: No such file or directory` é uma evidência de que o pseudo filesystem `/proc` não estava disponível na visão do processo.

Uma forma de preparar o rootfs a partir do ambiente hospedeiro é:

```bash
mount -t proc proc /data/local/linux/proc
```

Depois:

```bash
chroot /data/local/linux /bin/sh
ls /proc
```

> **Importante:** A montagem deve ser feita respeitando o namespace e as permissões do sistema hospedeiro. Não se deve assumir que `mount -t proc proc /proc` dentro do chroot produzirá automaticamente o comportamento desejado.

### 5.10 Disponibilizar /sys

Da mesma maneira:

```bash
mount -t sysfs sysfs /data/local/linux/sys
```

permite disponibilizar informações do kernel relacionadas ao sysfs, desde que o sistema e suas políticas de segurança permitam a operação.

### 5.11 Disponibilizar /dev

O diretório `/dev` é especialmente importante porque contém interfaces de dispositivos. Uma preparação típica pode utilizar:

```bash
mount --bind /dev /data/local/linux/dev
```

A operação deve ser feita a partir do ambiente hospedeiro, apontando o `/dev` real para o `/dev` correspondente dentro do rootfs. Não se deve confundir isso com `mount --bind /dev /dev` executado dentro do chroot. O segundo caso não representa corretamente a preparação do `/dev` do rootfs.

### 5.12 Disponibilizar /tmp

O `/tmp` pode utilizar um tmpfs quando o sistema permitir:

```bash
mount -t tmpfs tmpfs /data/local/linux/tmp
```

Isso cria uma área temporária baseada em memória. A disponibilidade e as opções permitidas dependem das políticas do kernel e do sistema hospedeiro.

## 7. Problemas comuns

### 7.1 `ls: not found` dentro do chroot

* **Causa provável:** O executável não está presente no rootfs ou o link aponta para um caminho pertencente ao sistema hospedeiro.
  * Exemplo problemático: `/bin/ls -> /system/xbin/busybox`
* **Diagnóstico (fora do chroot):**

```bash
ls -l /data/local/linux/bin/ls
ls -l /data/local/linux/bin/busybox
```

### 7.2 `mount: not found`

* **Causa provável:** O applet `mount` existe no BusyBox, mas não existe um executável acessível como `/bin/mount`.
* **Diagnóstico:** Verificar com `/bin/busybox mount`. Se isso funcionar, o problema é de disponibilização do applet, não necessariamente do BusyBox.

### 7.3 chroot encontra `/bin/sh`, mas não consegue executá-lo

* **Mensagem:** `No such file or directory`
* **Pode indicar:**
  * shell inexistente;
  * link simbólico quebrado;
  * ELF incompatível;
  * biblioteca dinâmica ausente;
  * loader ELF ausente.

Portanto, não se deve concluir imediatamente que o arquivo não existe.

### 7.4 ifconfig reclama de `/proc/net/dev`

* **Mensagem observada:** `ifconfig: /proc/net/dev: No such file or directory`
* **Causa:** O `/proc` não está disponível adequadamente no rootfs.
* **Solução:** Preparar a montagem de `/proc` para o rootfs.

### 7.5 `busybox --install` cria arquivos nos lugares errados

* **Comando problemático:** `busybox --install -s`
* Esse comando pode utilizar diretórios padrão que não correspondem ao rootfs. Em um ambiente de preparação, especificar explicitamente:

```bash
busybox --install -s /data/local/linux/bin
```

é muito mais seguro.

### 7.6 `chmod` retorna `Read-only file system`

Durante o projeto ocorreu `chmod 6755 /data/local/linux/bin/su` com `Unable to chmod ...: Read-only file system`.

Foi posteriormente confirmado `mount | grep '/data'` com:

```text
/emmc@usrdata /data ext4 rw,seclabel,relatime,discard,noauto_da_alloc,data=ordered 0 0
```

Portanto, não é correto concluir automaticamente que o `/data` estava montado somente para leitura. Também não é correto concluir automaticamente que o erro foi causado pelo SELinux.

O SELinux estava `Enforcing`, mas uma mensagem `Read-only file system` pode ter outras causas, incluindo:

* restrições específicas da operação;
* filesystem subjacente;
* contexto de segurança;
* política do kernel;
* comportamento do processo;
* limitações impostas pelo ambiente;
* diferenças entre o caminho visto pelo processo e o mount correspondente.

O diagnóstico correto exige investigar a operação específica antes de atribuir a causa.

### 8.3 Verificar identidade


* **Resultado observado:** `uid=0(root) gid=0(root)`

### 8.4 Verificar localização do BusyBox

```bash

```

* **Resultado:** `/system/xbin/busybox` e confirmação da versão.

Para um executável específico:

* **Exemplo observado:** `ls -> /system/xbin/busybox`

## 9. Segurança e riscos

O chroot é relativamente simples de experimentar, mas alterações no sistema hospedeiro podem ser perigosas.

### 9.1 Alteração de `/system`

Foi demonstrado que:

```bash
/system/xbin/busybox mount -o remount,rw /system
```

pode alterar o estado de montagem de `/system`. Isso deve ser tratado como operação de alto risco. Alterações incorretas em `/system` podem causar:

* falha de inicialização;
* aplicações quebradas;
* perda de funcionalidades;
* bootloop;
* necessidade de restaurar firmware.

### 9.2 Alteração de `/data`

O rootfs foi colocado em `/data/local/linux`. Alterações nessa área podem ser menos críticas para o boot do que alterações diretamente em `/system`, mas ainda podem afetar aplicações e dados.

Nunca se deve assumir que um diretório dentro de `/data` é descartável sem verificar sua função.

### 9.3 `su` e `setuid`

O BusyBox utilizado contém o applet `su`. Porém, *"BusyBox possui o applet su"* não significa *"su está configurado como root persistente"* nem *"setuid funcionará"*.

O comportamento depende das permissões, do kernel, do filesystem e das políticas de segurança. Além disso, alterar permissões para `6755` não deve ser utilizado como procedimento padrão sem antes compreender o contexto de segurança do aparelho.

### 9.4 SELinux

O aparelho possui SELinux em modo `Enforcing`. O SELinux deve ser considerado uma camada independente das permissões Unix tradicionais:

```text
UID/GID
   ↓
permissões Unix
   ↓
filesystem
   ↓
mount flags
   ↓
SELinux
   ↓
kernel
```

Uma operação pode ser permitida em uma camada e bloqueada em outra.

## 10. Compatibilidade

O ambiente descrito nesta seção depende fortemente do dispositivo.

### 10.1 KaiOS

O aparelho utilizado possui **KaiOS 2.5.1.2**. Outras versões podem possuir:

* BusyBox diferente;
* kernel diferente;
* políticas SELinux diferentes;
* layout de partições diferente;
* permissões diferentes;
* runtime diferente;
* mecanismos diferentes de inicialização.

### 10.2 Arquitetura

O Zapp II investigado utiliza **ARMv7**. Portando, binários compilados para `ARM64`, `x86` ou `x86_64` não devem ser presumidos como executáveis.

### 10.3 Kernel

O kernel observado no aparelho é **Linux 3.4.67**.

Isso é particularmente importante. Um binário moderno pode depender de funcionalidades de kernel que não existem nessa versão. Da mesma forma, ferramentas compiladas para sistemas Linux modernos podem não ser compatíveis com a ABI disponível no aparelho.

### 10.4 BusyBox

O BusyBox utilizado é o **1.21.1**.

Trata-se de uma versão antiga. Comandos e opções disponíveis nessa versão podem ser diferentes daqueles encontrados em BusyBox contemporâneo. Portanto, documentação baseada em BusyBox 1.36+, por exemplo, não deve ser aplicada automaticamente ao Zapp II.

## 12. Resumo

O Zapp II demonstrou ser capaz de executar um ambiente Linux adicional por meio de chroot, utilizando um rootfs localizado em `/data/local/linux`.

O ambiente utiliza o kernel do sistema hospedeiro e não constitui uma máquina virtual independente. O BusyBox disponível no sistema é `/system/xbin/busybox`, versão `1.21.1`.

O shell do mini-Linux foi executado com `chroot /data/local/linux /bin/sh` e foi confirmado `uid=0(root) gid=0(root)`.

A conectividade de rede também foi comprovada:

```bash
/bin/busybox ping -c 3 8.8.8.8
```

com `3 packets transmitted, 3 packets received, 0% packet loss`. A interface `wlan0` foi identificada dentro do ambiente.

Um dos principais problemas encontrados foi a criação de links simbólicos que apontavam para `/system/xbin/busybox` a partir do rootfs. Como o chroot altera a raiz percebida pelo processo, esses links podem não apontar para o BusyBox do sistema hospedeiro quando utilizados dentro do ambiente.

Outro ponto importante é a disponibilidade de pseudo sistemas de arquivos como `/proc`, `/sys` e `/dev`. O erro `/proc/net/dev: No such file or directory` demonstrou que a disponibilidade desses sistemas é necessária para determinadas ferramentas funcionarem corretamente.

Por fim, o aparelho possui SELinux `Enforcing` e `/data` foi confirmado como `ext4 rw`. Portanto, operações envolvendo permissões, `su`, `setuid` e modificações do sistema devem ser analisadas considerando simultaneamente o filesystem, os mount flags, as permissões Unix, o SELinux e o kernel.

O resultado mais importante desta etapa é que o Zapp II já possui uma base suficiente para funcionar como um ambiente Linux experimental independente em nível de userland, sem substituir o sistema principal.
