# ADB via USB no KaiOS: diagnóstico de desconexões cíclicas em dispositivos MediaTek

## 1. Visão geral

O ADB (*Android Debug Bridge*) é utilizado por dispositivos KaiOS para fornecer uma interface de depuração entre o computador e o sistema do aparelho. Embora o KaiOS não seja Android, determinadas versões utilizam o protocolo ADB e o daemon `adbd` para depuração e comunicação com ferramentas de desenvolvimento. A documentação oficial do KaiOS descreve o uso de `adb devices` e `adb root` para verificar dispositivos de desenvolvimento.

Em aparelhos KaiOS baseados em MediaTek, uma falha particularmente interessante ocorre quando:

1. O computador reconhece o dispositivo;
2. `adb devices` mostra o aparelho como `device`;
3. `adb shell` consegue abrir uma sessão;
4. A sessão desaparece poucos segundos depois;
5. O dispositivo volta a aparecer;
6. O ciclo se repete.

Esse comportamento deve ser distinguido de uma simples falha de autorização ADB.

No caso analisado nesta seção, o Multilaser Zapp II, equipado com MediaTek MT6572 e KaiOS 2.5.1.2, apresentou exatamente esse padrão. O diagnóstico foi baseado nos logs do kernel capturados durante a desconexão.

> **Conclusão principal da investigação:** os logs fornecidos indicam que a desconexão não é simplesmente causada pelo encerramento do processo `adbd`. O próprio subsistema USB/MUSB está sendo desativado e reativado repetidamente. Portanto, a investigação deve se concentrar na camada USB, no driver MUSB, no gerenciamento de energia/PHY e na forma como o firmware configura o gadget ADB.

---

## 2. Conceitos fundamentais

### 2.1 ADB não é o mesmo que Android

O uso de `adb` não significa que o dispositivo esteja executando Android.

No KaiOS, o ADB pode ser utilizado como mecanismo de comunicação com o sistema. A própria comunidade KaiOS documenta ADB e depuração em aparelhos KaiOS 2.5, inclusive em dispositivos MediaTek.

Portanto, comandos como:
- `adb devices`
- `adb shell`
- `adb root`
- `adb logcat`

não devem ser interpretados como evidência de que o sistema operacional do aparelho é Android.

### 2.2 adbd

`adbd` é o daemon responsável pelo lado do dispositivo da comunicação ADB.

No cenário estudado, entretanto, existem vários níveis envolvidos:

```text
Computador
    │
    │ USB
    ▼
Controladora USB do PC
    │
    ▼
USB Device Controller do Zapp II
    │
    ▼
MUSB
    │
    ▼
USB Gadget
    │
    ▼
ADB Function
    │
    ▼
adbd
    │
    ▼
shell / sistema KaiOS
```

Consequentemente, uma desconexão observada pelo computador como `device → desconectado` não significa necessariamente `adbd → morreu`. O problema pode ocorrer antes disso, na camada USB.

### 2.3 MUSB

O log do Zapp II identifica explicitamente o controlador USB como `[MUSB]`.

MUSB é o controlador USB utilizado por diversas plataformas embarcadas, incluindo plataformas MediaTek dessa geração. No log analisado aparecem funções como:
- `musb_gadget_pullup`
- `musb_pullup`
- `musb_start`
- `musb_stop`
- `mt_usb_enable`
- `mt_usb_disable`

Isso é particularmente importante porque permite observar o comportamento do controlador USB diretamente.

### 2.4 USB Gadget

No modo conectado ao computador, o Zapp II atua como dispositivo USB, ou seja, como *USB gadget*.

O log apresenta:
- `[USB] android_bind_enabled_functions`
- `[USB] usb_add_function`
- `f_adb.c adb_bind_config`

Isso demonstra que a função USB associada ao ADB está sendo configurada.

## 3. Como funciona

Uma conexão USB ADB funcional pode ser simplificada da seguinte maneira:

```text
adbd
  │
  ▼
ADB USB function
  │
  ▼
USB Gadget
  │
  ▼
MUSB
  │
  ▼
USB PHY
  │
  ▼
porta USB física
  │
  ▼
computador
```

Durante uma reconexão, esperamos encontrar eventos semelhantes a `adb_open`, seguidos pela ativação da interface USB.

No log do Zapp II aparece:
1. `adb_open start`
2. `musb_gadget_pullup ... is_on=1`
3. `adb_open end`

Isso indica que o sistema consegue configurar novamente a interface. O problema é que, aproximadamente dois segundos depois, ocorre novamente:
1. `adb_release start`
2. `android_disconnect`
3. `musb_stop`

Após isso, o sistema volta a executar `adb_open`.

Assim, o padrão observado é:

```text
ADB/USB abre
      ↓
USB é ativado
      ↓
USB é desconectado
      ↓
USB é desativado
      ↓
adbd associado à sessão termina
      ↓
USB é reconfigurado
      ↓
ADB abre novamente
      ↓
...
```

Esse ciclo é o principal elemento diagnóstico do caso.

| Componente | Função no diagnóstico |
| :--- | :--- |
| `adb` | Cliente ADB no computador |
| `adbd` | Daemon ADB no Zapp II |
| **USB Gadget** | Expõe o ADB como função USB |

| **Kernel Linux 3.4** | Kernel identificado no firmware analisado |

O próprio log fornece uma evidência particularmente útil sobre a árvore de código utilizada na compilação:

```text
/home/ap-3-x9/workspace/zhouc/kaios_72_R1_512S/kernel-3.4/drivers/usb/gadget/f_adb.c
```

Esse caminho não deve ser interpretado como um caminho existente no aparelho. Ele é, aparentemente, o caminho do ambiente de compilação utilizado pelo fabricante. Ele é, entretanto, uma evidência valiosa sobre a origem do código do kernel.

## 5. Procedimentos práticos

### 5.1 Confirmar qual dispositivo ADB está sendo utilizado

Quando o Zapp II está simultaneamente conectado por USB e Wi-Fi, o ADB pode apresentar:

```text
error: more than one device/emulator
```

Nesse caso, utilize o identificador explicitamente.

Para o Zapp II conectado via Wi-Fi:
```bash
adb -s 192.168.0.16:5555 shell
```

Para verificar os dispositivos:
```bash
adb devices
```

Exemplo de saída:
```text
List of devices attached
192.168.0.16:5555       device
AIQ4Q85PWK4L6PEU        device
```

O primeiro é a conexão Wi-Fi. O segundo é a conexão USB.

### 5.2 Capturar o log do dispositivo via Wi-Fi

A conexão Wi-Fi é particularmente útil neste diagnóstico porque permite investigar o subsistema USB sem depender da estabilidade do ADB USB.

Exemplo para capturar o dmesg:
```bash
adb -s 192.168.0.16:5555 shell dmesg
```

Para procurar mensagens relacionadas a USB:
```bash
adb -s 192.168.0.16:5555 shell dmesg | grep -i usb
```

Para procurar MUSB:
```bash
adb -s 192.168.0.16:5555 shell dmesg | grep -i musb
```

Para procurar ADB:
```bash
adb -s 192.168.0.16:5555 shell dmesg | grep -i adb
```

Uma estratégia mais ampla:
```bash
adb -s 192.168.0.16:5555 shell dmesg | grep -Ei 'adb|usb|musb|phy|gadget'
```

Essa abordagem é preferível a procurar exclusivamente por `adbd`.

### 5.3 Capturar o log durante a falha

Como o problema ocorre rapidamente, a melhor metodologia é:

1. Estabelecer ADB via Wi-Fi;
2. Iniciar a captura;
3. Conectar o USB;
4. Aguardar a falha;
5. Preservar o log;
6. Somente depois realizar alterações no sistema.

Exemplo de comando:
```bash
adb -s 192.168.0.16:5555 shell dmesg > zapp2_usb_dmesg.txt
```

Para acompanhamento em tempo real:
```bash
adb -s 192.168.0.16:5555 shell dmesg -w
```

*Nota: A disponibilidade de `dmesg -w` depende da implementação presente no firmware. Portanto, se essa opção não funcionar, deve-se utilizar uma captura convencional de `dmesg`.*

## 6. Evidência encontrada no Zapp II

O trecho mais importante do log fornecido é:

1. `adb_release start` seguido imediatamente por `musb_gadget_pullup ... is_on=0`
2. `android_disconnect`
3. `dev->connected = 0`
4. `mt_usb_disable`
5. `musb_stop`

Isso constitui uma sequência coerente de desconexão do gadget USB.

Logo depois, o kernel começa novamente a montar a função ADB:
1. `adb_open start`
2. `android_bind_enabled_functions`
3. `usb_add_function`
4. `f_adb.c adb_bind_config`
5. `musb_gadget_pullup ... is_on=1`
6. `adb_open end`

Ou seja:

```text
                    ┌──────────────────────┐
                    │      adb_open        │
                    └──────────┬───────────┘
                               │
                               ▼
                     USB gadget ativo
                               │
                               ▼
                        ADB disponível
                               │
                               ▼
                    ┌──────────────────────┐
                    │     adb_release      │
                    └──────────┬───────────┘
                               │
                               ▼
                      android_disconnect
                               │
                               ▼
                        mt_usb_disable
                               │
                               ▼
                          musb_stop
                               │
                               ▼
                     USB gadget desligado
                               │
                               ▼
                         adb_open novamente
```

O ciclo aparece diversas vezes no intervalo de poucos segundos.

## 7. Interpretação do `adb_release`

É importante não interpretar `adb_release` automaticamente como *"O adbd decidiu encerrar porque encontrou um erro."*

O log fornecido não demonstra isso. A sequência mostra que `adb_release` está associada à liberação da interface USB:

```text
adb_release start → android_disconnect → mt_usb_disable → musb_stop
```

Portanto, uma hipótese mais consistente com as evidências é:
> A sessão ADB está sendo encerrada como consequência da desconexão da função USB, e não necessariamente porque o `adbd` apresentou uma falha primária.

Essa distinção é fundamental para o *debugging*.

---

## 8. Evidência importante sobre o USB PHY

O log contém:
- `usb_phy_savecurrent_internal`
- `usb save current success`

E posteriormente, durante a reconexão:
- `[USBPHY]slew calibration`
- `usb recovery success`

Isso demonstra que o firmware está realizando operações explícitas de gerenciamento e recuperação do USB PHY.

A presença de `usb recovery success` é especialmente interessante. Ela indica que o código do controlador considera que houve uma condição na qual uma recuperação da interface USB foi necessária.

Entretanto, não é possível concluir apenas por essa mensagem que a causa raiz seja um defeito físico do PHY. O log demonstra a recuperação, mas não demonstra por que a recuperação foi necessária.

---

## 9. Mensagem "Charger exist and USB is not host"

Uma mensagem recorrente é:

```text
[Power/Battery] [upmu_is_chr_det] Charger exist and USB is not host
```

Ela merece atenção, mas não deve ser interpretada isoladamente como *"O aparelho está reconhecendo o computador apenas como carregador."* Essa conclusão seria excessiva.

A mensagem está sendo emitida durante a ativação/desativação do subsistema USB e provavelmente está relacionada à lógica de detecção de carregador/host do hardware MediaTek.

Mais importante é observar o conjunto:

```text
Charger exist and USB is not host
    + musb_gadget_pullup
    + android_disconnect
    + mt_usb_disable
    + musb_stop
```

**Diagnóstico correto:** Existe uma interação anormal entre a lógica de detecção USB/power e o modo gadget do controlador MUSB. Ainda não é possível determinar, apenas com esse log, se a causa é cabo, porta, hardware, configuração de firmware, gerenciamento de energia ou bug do driver.

---

## 10. Mensagens sobre o clock USB

O log também apresenta:
- `musb_readl: access musb_readl function when usb clock is off`
- `musb_writel: access musb_writel function when usb clock is off`

Essas mensagens são relevantes. Elas indicam que determinadas operações de leitura/escrita nos registradores MUSB estão ocorrendo quando o clock USB está desligado.

Entretanto, novamente, isso não deve ser automaticamente classificado como "o erro". É possível que essas mensagens façam parte de uma sequência normal de transição de energia do driver, especialmente durante a ativação ou desativação do controlador.

A hipótese mais interessante é investigar se a sequência:

```text
clock USB ──> MUSB ──> USB PHY ──> gadget
```

está entrando em uma condição de desligamento/reinicialização inesperada.

## 11. O que o log descarta ou enfraquece

O log fornece evidências contra algumas hipóteses.

### 11.1 "O ADB não está funcionando"
**Não.** O ADB funciona. O dispositivo chegou a `device` e a sessão shell chegou a `root@ZAPP_II:/ #`. Além disso, o log mostra repetidamente a criação da função ADB.

### 11.2 "O adbd simplesmente morreu"
Não há evidência suficiente para afirmar isso. O log mostra processos filhos `adbd` terminando (`[2364:adbd] exit`), mas isso acontece dentro de uma sequência de `adb_release` e desconexão USB. É mais consistente interpretar esses processos como associados às sessões/conexões que estão sendo encerradas.

### 11.3 "O problema é necessariamente o cabo"
Também não está comprovado. Um cabo defeituoso continua sendo uma hipótese válida, especialmente se o problema ocorrer somente em determinada conexão física. Mas o log demonstra atividade interna no controlador USB do aparelho, portanto não devemos encerrar o diagnóstico simplesmente substituindo o cabo.

---

## 12. Teste diferencial USB versus Wi-Fi

Esse é um dos testes mais importantes. O Zapp II apresentou uma conexão `192.168.0.16:5555 device` e `adb -s 192.168.0.16:5555 shell` funcionando como root.

Isso permite separar duas camadas:

| Teste | Resultado | Interpretação |
| :--- | :--- | :--- |
| **ADB via Wi-Fi** | Funciona | `adbd` e shell estão operacionais |
| **ADB via USB** | Desconecta | Problema associado à camada USB ou à sua configuração |
| **adb root via Wi-Fi** | `adbd is already running as root` | Daemon está funcional e privilegiado |
| **USB gadget** | Reinicia repetidamente | Forte evidência de problema no caminho USB |

Essa comparação é muito mais informativa do que simplesmente executar `adb shell` várias vezes.

## 13. Procedimento recomendado para investigação

### Etapa 1: manter o Wi-Fi ADB funcional
```bash
adb devices
# Esperado: 192.168.0.16:5555       device

adb -s 192.168.0.16:5555 shell
```

### Etapa 2: verificar o kernel
```bash
adb -s 192.168.0.16:5555 shell uname -a
adb -s 192.168.0.16:5555 shell cat /proc/version
```

### Etapa 3: capturar o estado USB antes da conexão
```bash
adb -s 192.168.0.16:5555 shell dmesg > zapp2_before_usb.txt
```

### Etapa 4: conectar o USB
Conectar o cabo sem executar imediatamente vários comandos ADB. Observar no computador:
```bash
adb devices
```

### Etapa 5: capturar novamente via Wi-Fi
Enquanto o ADB Wi-Fi permanecer disponível:
```bash
adb -s 192.168.0.16:5555 shell dmesg > zapp2_after_usb.txt
```

### Etapa 6: comparar
```bash
grep -Ei 'adb|usb|musb|phy|gadget|charger' zapp2_after_usb.txt
```

Uma investigação mais precisa pode utilizar:
```bash
grep -Ei 'disconnect|connect|release|open|disable|enable|recovery|clock|phy' zapp2_after_usb.txt
```

## 14. O que procurar em um log futuro

Durante uma nova captura, os eventos mais importantes são:

### Eventos de desconexão
- `android_disconnect`
- `dev->connected = 0`
- `musb_stop`
- `mt_usb_disable`
- `adb_release`

### Eventos de reconexão
- `adb_open`
- `usb_add_function`
- `adb_bind_config`
- `musb_start`
- `mt_usb_enable`
- `adb_open end`

### Eventos potencialmente anormais
- `USBPHY`
- `usb recovery`
- `clock is off`
- `reset`
- `error`
- `timeout`
- `over-current`
- `overcurrent`
- `enumeration failed`

Também devem ser procuradas mensagens que apareçam imediatamente antes da primeira ocorrência de `adb_release`. Essa é uma das partes mais importantes do diagnóstico: **o evento que inicia o ciclo é mais relevante que os eventos posteriores de recuperação**.

## 16. Segurança e riscos

A investigação inicial deve ser somente observacional.

Comandos como `dmesg`, `adb devices`, `adb shell`, `uname -a` e `cat /proc/version` são preferíveis inicialmente porque não modificam o sistema.

Não é recomendável começar o diagnóstico alterando:
- `/system`
- `/init`
- `build.prop`
- propriedades USB
- scripts de boot
- kernel
- `boot.img`

sem antes preservar os logs.

Especialmente em um dispositivo no qual já existe acesso root, comandos como `setprop`, `stop adbd` e `start adbd` podem alterar o estado de depuração e destruir justamente a condição que está sendo investigada.

A documentação oficial do KaiOS confirma que o ADB faz parte do fluxo de desenvolvimento em dispositivos de debug, mas o comportamento concreto de cada aparelho depende da implementação do fabricante.

## 17. Compatibilidade

O comportamento descrito nesta seção não deve ser generalizado para todos os dispositivos KaiOS.

O caso analisado possui características específicas:
- **Modelo:** Multilaser Zapp II
- **SoC:** MediaTek MT6572
- **KaiOS:** 2.5.1.2
- **Kernel:** Linux 3.4
- **Controlador USB observado:** MUSB

A comunidade KaiOS registra que dispositivos MediaTek possuem particularidades próprias em relação à depuração e modificação, e existem diferenças importantes entre aparelhos mesmo dentro da mesma versão do KaiOS. Além disso, versões posteriores do KaiOS podem alterar significativamente o acesso ao ADB e às ferramentas de desenvolvimento.

> **Portanto:** Os comandos básicos ADB são relativamente portáveis, mas o diagnóstico interno de USB, `adbd`, MUSB, PHY e firmware é específico da plataforma.

## 19. Resumo

O caso do Zapp II demonstra uma distinção importante no diagnóstico de ADB:

`ADB desconectando` ≠ `adbd necessariamente com defeito`

Os logs fornecidos mostram repetidamente a seguinte sequência:

```text
adb_release
    ↓
musb_gadget_pullup(is_on=0)
    ↓
android_disconnect
    ↓
dev->connected = 0
    ↓
mt_usb_disable
    ↓
musb_stop
    ↓
adb_open
    ↓
usb_add_function
    ↓
adb_bind_config
    ↓
musb_gadget_pullup(is_on=1)
    ↓
usb recovery
    ↓
adb_open end
```

A repetição desse ciclo demonstra que o subsistema USB do Zapp II está sendo desativado e reativado repetidamente.

A evidência atual favorece uma investigação concentrada em:
1. Controlador MUSB;
2. USB gadget;
3. USB PHY;
4. Gerenciamento de energia USB;
5. Detecção host/carregador;
6. Configuração do firmware;
7. Eventualmente, cabo, porta ou hardware físico.

O funcionamento do ADB via Wi-Fi é uma evidência importante porque demonstra que o `adbd` e o shell do aparelho permanecem operacionais fora do caminho USB.

A próxima informação mais valiosa para determinar a causa raiz não é simplesmente mais uma captura do mesmo ciclo, mas o trecho imediatamente anterior à primeira ocorrência de `adb_release`, preferencialmente incluindo todas as mensagens do kernel relacionadas a USB, PHY, energia e MUSB.
