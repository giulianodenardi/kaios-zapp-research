# Servidor HTTP local no KaiOS

## 1. Visão geral

Um dispositivo KaiOS possui, além da camada de aplicações e da interface baseada em Gecko, uma camada de baixo nível chamada **Gonk**, responsável pelo kernel Linux, bibliotecas do sistema, firmware e drivers [cite: 5]. A documentação oficial descreve Gonk como a camada subjacente sobre a qual o Gecko é executado [cite: 5]. 

Essa arquitetura permite que, em aparelhos nos quais exista acesso ao shell do sistema, determinadas ferramentas Linux possam ser executadas independentemente da interface gráfica do KaiOS [cite: 5].

Um exemplo particularmente útil é o **BusyBox httpd**, um servidor HTTP compacto capaz de publicar arquivos de um diretório através da rede local [cite: 5]. O `httpd` faz parte do conjunto de applets do BusyBox e possui opções para definir porta, endereço de escuta, diretório raiz e modo foreground [cite: 5]. 

No contexto deste projeto, isso permite transformar o aparelho em um servidor web local, de maneira semelhante ao uso de:

```bash
python3 -m http.server
```

em um computador Linux [cite: 5].

É importante distinguir duas coisas [cite: 5]:

* **Servidor HTTP no sistema do aparelho:** executado pelo Linux/Gonk, por exemplo através do BusyBox [cite: 5]. 
* **Aplicação web KaiOS:** executada pelo Gecko e sujeita às APIs e ao modelo de segurança do KaiOS [cite: 5]. 

O primeiro não depende necessariamente da existência de uma aplicação KaiOS para funcionar [cite: 5].

## 2. Conceitos fundamentais

### 2.1 HTTP

HTTP é o protocolo utilizado para comunicação entre clientes e servidores web [cite: 5].

Em uma configuração simples [cite: 5]:

```text
PC / navegador
      │
      │ HTTP
      ▼
┌─────────────────┐
│     Zapp II     │
│                 │
│ BusyBox httpd   │
│       │         │
│       ▼         │
│   /www          │
└─────────────────┘
```

O navegador solicita, por exemplo: `GET /index.html` e o servidor responde com o conteúdo do arquivo [cite: 5].

### 2.2 Servidor HTTP

Um servidor HTTP associa [cite: 5]:

1. Um endereço IP [cite: 5]; 
2. Uma porta TCP [cite: 5]; 
3. Um diretório usado como raiz do servidor [cite: 5]. 

Por exemplo:

* **IP:** `192.168.0.16` [cite: 5]
* **Porta:** `8080` [cite: 5]
* **Diretório:** `/storage/sdcard1/www` [cite: 5]

O endereço correspondente seria: `http://192.168.0.16:8080/` [cite: 5]

### 2.3 Diretório raiz HTTP

O diretório definido através da opção `-h` do BusyBox httpd funciona como a raiz dos arquivos publicados [cite: 5].

Se `/storage/sdcard1/www/index.html` existir, uma solicitação para `/` poderá resultar na entrega de `index.html` [cite: 5].
O BusyBox documenta `-h HOME` como a opção que define o diretório inicial do servidor [cite: 5]. 

### 2.4 Foreground e daemon

O `httpd` pode ser executado em foreground [cite: 5]:

```bash
busybox httpd -f ...
```

Nesse modo, o processo permanece associado ao terminal [cite: 5]. Isso é particularmente útil durante testes porque permite observar imediatamente se o servidor iniciou corretamente [cite: 5].

Sem `-f`, o comportamento normal é executar o servidor em background. A documentação do BusyBox descreve `-f` como *"Don't daemonize"* [cite: 5].

## 3. Como funciona

O fluxo básico é [cite: 5]:

```text
1. Criar diretório web
        ↓
2. Colocar arquivos no diretório
        ↓
3. Iniciar BusyBox httpd
        ↓
4. httpd abre uma porta TCP
        ↓
5. Outro dispositivo conecta ao IP do KaiOS
        ↓
6. Navegador solicita arquivos
        ↓
7. httpd entrega os arquivos
```

Por exemplo:

```text
/storage/sdcard1/www/
├── index.html
├── style.css
├── script.js
└── imagens/
    └── logo.png
```

O navegador poderá acessar `http://192.168.0.16:8080/` e solicitar [cite: 5]:

* `/index.html` [cite: 5]
* `/style.css` [cite: 5]
* `/script.js` [cite: 5]
* `/imagens/logo.png` [cite: 5]

O servidor simplesmente mapeia essas solicitações para os arquivos existentes no diretório raiz [cite: 5].

## 4. Componentes envolvidos

| Componente | Função |
| :--- | :--- |
| **Linux/Gonk** | Fornece a infraestrutura de execução e rede |
| **BusyBox** | Fornece ferramentas Unix compactas |
| **httpd** | Servidor HTTP |
| **Interface de rede** | Fornece conectividade IP |
| **TCP** | Transporte das conexões HTTP |
| **Navegador** | Cliente HTTP |
| **Diretório web** | Contém os arquivos publicados |
| `/storage/sdcard1` | Armazenamento externo, quando disponível no aparelho |

No Zapp II investigado neste projeto, já foi identificado um ambiente Linux com BusyBox, acesso root e ferramentas de rede [cite: 5].
A presença de um determinado applet, entretanto, deve ser verificada no aparelho, pois o BusyBox pode ser compilado com diferentes conjuntos de funcionalidades [cite: 5].

## 5. Procedimentos práticos

### 5.1 Verificar se o BusyBox possui httpd

* **Objetivo:** Confirmar que o BusyBox instalado possui o servidor HTTP [cite: 5].
* **Pré-requisitos:** Acesso ao shell e BusyBox instalado [cite: 5].

**Comando:**

```bash
busybox --list | grep httpd
```

Outra possibilidade:

```bash
busybox httpd --help
```

**Resultado esperado:**
Caso o applet esteja disponível, deverá aparecer uma referência a `httpd` ou uma mensagem de uso semelhante a:

```text
httpd [-ifv[v]] ...
```

As opções documentadas incluem `-f`, `-p` e `-h` [cite: 5]. 

**Possíveis erros:**
Se aparecer algo semelhante a `httpd: applet not found`, o BusyBox instalado não possui esse applet [cite: 5]. Nesse caso, não se deve presumir que qualquer comando `busybox httpd` funcionará [cite: 5].

### 5.2 Criar um diretório para o site

* **Objetivo:** Criar uma área isolada para os arquivos que serão publicados [cite: 5].

No Zapp II, um exemplo é:

```bash
mkdir -p /storage/sdcard1/www
```

Verifique:

```bash
ls -la /storage/sdcard1/www
```

### 5.3 Criar uma página de teste

Pode-se criar uma página diretamente no dispositivo:

```bash
cat > /storage/sdcard1/www/index.html <<'EOF'
<!DOCTYPE html>
<html>
<head>
    <meta charset="utf-8">
    <title>Zapp II</title>
</head>
<body>
    <h1>Servidor HTTP do Zapp II</h1>
    <p>Servidor funcionando.</p>
</body>
</html>
EOF
```

Verifique:

```bash
cat /storage/sdcard1/www/index.html
```

### 5.4 Iniciar o servidor em uma porta não privileged

* **Objetivo:** Executar o servidor para testes sem utilizar a porta HTTP tradicional 80 [cite: 5].

```bash
busybox httpd -f -p 8080 -h /storage/sdcard1/www
```

Os parâmetros significam [cite: 5]:

| Parâmetro | Função |
| :--- | :--- |
| `-f` | Mantém o servidor em foreground |
| `-p 8080` | Utiliza a porta TCP 8080 |
| `-h ...` | Define a raiz dos arquivos |

Essas opções fazem parte da interface documentada do httpd do BusyBox [cite: 5]. 

### 5.5 Acessar o servidor

Descubra o endereço IP do aparelho [cite: 5]. Dependendo das ferramentas disponíveis:

```bash
ip addr
```

ou:

```bash
ifconfig
```

Supondo que o aparelho tenha `192.168.0.16` e o servidor esteja na porta `8080`, o computador poderá acessar `http://192.168.0.16:8080/` [cite: 5].
A URL deve ser digitada no navegador do computador conectado à mesma rede [cite: 5].

### 5.6 Testar sem navegador

Um cliente HTTP de linha de comando pode ser utilizado para verificar se o servidor realmente está respondendo [cite: 5].

No computador:

```bash
curl http://192.168.0.16:8080/
```

O conteúdo de `index.html` deverá aparecer no terminal [cite: 5]. Esse método é particularmente útil para debugging porque separa problemas do servidor de problemas relacionados ao navegador [cite: 5].

### 5.7 Executar em background

Depois de confirmar que o servidor funciona, pode-se executá-lo sem `-f` [cite: 5]:

```bash
busybox httpd -p 8080 -h /storage/sdcard1/www
```

O processo passa a funcionar em background [cite: 5].
Verifique:

```bash
ps | grep httpd
```

O comportamento de daemonização é justamente o motivo pelo qual o `-f` é útil durante a fase de diagnóstico [cite: 5]. 

### 5.8 Encerrar o servidor

Identifique o processo:

```bash
ps | grep httpd
```

Depois, encerre-o usando o mecanismo disponível no sistema [cite: 5]. Por exemplo:

```bash
kill PID
```

onde `PID` corresponde ao identificador do processo [cite: 5].
Evita-se utilizar um `kill` genérico contra processos não identificados, especialmente em um sistema embarcado com acesso root [cite: 5].

## 6. Exemplos

### 6.1 Site estático completo

**Estrutura:**

```text
/storage/sdcard1/www/
├── index.html
├── style.css
├── app.js
└── imagens/
    └── logo.png
```

**Servidor:**

```bash
busybox httpd -p 8080 -h /storage/sdcard1/www
```

**Acesso:**
`http://IP_DO_ZAPP:8080/`

Isso é suficiente para hospedar páginas HTML, CSS, JavaScript, imagens e outros arquivos estáticos que o `httpd` consiga servir [cite: 5].

### 6.2 Usar o Zapp II como servidor de arquivos

O mesmo mecanismo pode ser utilizado para disponibilizar arquivos através de HTTP [cite: 5].

Por exemplo:

```text
/storage/sdcard1/www/
├── backup.tar.gz
├── firmware/
│   └── firmware.bin
└── documentos/
    └── manual.pdf
```

O navegador poderá acessar os arquivos através das respectivas URLs [cite: 5].
Entretanto, isso deve ser tratado como servidor de arquivos em rede local, e não como mecanismo de transferência autenticada [cite: 5].

### 6.3 Comparação com Python

Em um computador Linux:

```bash
python3 -m http.server 8080
```

No Zapp II:

```bash
busybox httpd -p 8080 -h /storage/sdcard1/www
```

Conceitualmente, os dois fazem a mesma coisa:

```text
diretório
    ↓
servidor HTTP
    ↓
porta TCP
    ↓
navegador
```

A implementação, entretanto, é diferente [cite: 5].
O Python fornece um runtime completo e um servidor implementado em Python [cite: 5]. O BusyBox httpd é um servidor HTTP compacto integrado ao próprio BusyBox [cite: 5].

## 7. Problemas comuns

* **`httpd: applet not found`**  
  Indica que o BusyBox instalado não contém o applet httpd [cite: 5].  
  *Verificação:* `busybox --list | grep httpd` [cite: 5]

* **`Connection refused`**  
  Normalmente significa que não existe um processo escutando naquela porta ou que a conexão está sendo recusada [cite: 5].  
  *No aparelho:* `ps | grep httpd`  
  Também pode ser necessário verificar a interface de rede: `ip addr` [cite: 5]

* **`Connection timed out`**  
  É mais compatível com problemas de conectividade ou filtragem de rede [cite: 5].  
  *Verifique primeiro:* `ping IP_DO_ZAPP` [cite: 5]  
  Se houver conectividade IP, investigue firewall e a porta utilizada [cite: 5].

* **Página não encontrada**  
  Confirme o diretório: `ls -la /storage/sdcard1/www` e confirme que o servidor foi iniciado usando exatamente esse diretório:  
  `busybox httpd -f -p 8080 -h /storage/sdcard1/www` [cite: 5]

* **Porta 80 não funciona**  
  A porta 80 é uma porta privilegiada em sistemas Unix tradicionais. Além disso, pode existir outro serviço utilizando-a [cite: 5].  
  Para testes, uma porta alta como `8080` é preferível [cite: 5].

## 8. Diagnóstico e debugging

O primeiro princípio é testar cada camada separadamente [cite: 5].

1. **Confirmar o applet:**
   ```bash
   busybox httpd --help
   ```
2. **Confirmar o diretório:**
   ```bash
   ls -la /storage/sdcard1/www
   ```
3. **Confirmar a interface de rede:**
   ```bash
   ip addr
   ```
4. **Executar em foreground:**
   ```bash
   busybox httpd -f -p 8080 -h /storage/sdcard1/www
   ```
   Esse é o modo mais apropriado para o primeiro teste porque o processo não é imediatamente colocado em background [cite: 5].
5. **Verificar o processo (em outro shell):**
   ```bash
   ps | grep httpd
   ```
6. **Testar pelo próprio aparelho:**
   Se houver um cliente HTTP compatível, pode-se testar contra o endereço local [cite: 5]. Caso contrário, o teste pode ser realizado a partir de outro computador [cite: 5].
7. **Testar com `curl` no computador:**
   ```bash
   curl -v http://IP_DO_ZAPP:8080/
   ```
   A opção `-v` permite observar detalhes da conexão HTTP e ajuda a distinguir: *problema de rede* de *problema HTTP* de *problema no arquivo solicitado* [cite: 5].

## 9. Segurança e riscos

O `httpd` do BusyBox é apropriado para testes e serviços simples, mas não deve ser tratado automaticamente como um servidor web público seguro [cite: 5].

### 9.1 Ausência de autenticação

Uma configuração simples como:

```bash
busybox httpd -p 8080 -h /storage/sdcard1/www
```

não deve ser presumida como protegida por autenticação [cite: 5]. Qualquer dispositivo capaz de alcançar a porta poderá tentar acessar o servidor [cite: 5].

### 9.2 Exposição de arquivos

O diretório definido por `-h` é a área publicada pelo servidor [cite: 5]. Portanto, não é recomendável utilizar diretamente como raiz um diretório que contenha informações privadas [cite: 5].

* **Preferível:** `/storage/sdcard1/www` [cite: 5]
* **Evitar:** `/data` ou outros diretórios contendo dados internos do sistema [cite: 5].

### 9.3 Rede local não significa automaticamente rede segura

Um servidor destinado apenas à rede local ainda pode ser acessível por outros dispositivos conectados à mesma rede [cite: 5]. Isso é especialmente importante em redes públicas ou compartilhadas [cite: 5].

### 9.4 Não alterar `/system` para instalar o servidor

Se o BusyBox já estiver disponível, não há necessidade de substituir arquivos do sistema apenas para executar `httpd` [cite: 5].
A abordagem preferível durante investigação é utilizar os arquivos já existentes e manter as alterações fora das partições críticas [cite: 5].

No Zapp II investigado neste projeto, o acesso root permite realizar experimentos desse tipo sem modificar imediatamente a imagem do sistema [cite: 5].

## 10. Compatibilidade

* **KaiOS 2.5:** KaiOS 2.5 utiliza uma arquitetura baseada em Gecko 48, enquanto versões posteriores da plataforma possuem componentes significativamente diferentes [cite: 5]. Portanto, não se deve assumir que um procedimento realizado em KaiOS 2.5 será idêntico em KaiOS 3.x ou versões posteriores [cite: 5].
* **BusyBox:** A disponibilidade do `httpd` depende da configuração usada para compilar o BusyBox [cite: 5]. No aparelho investigado neste projeto foi identificada a versão `BusyBox v1.21.1` [cite: 5]. Entretanto, a versão sozinha não garante que todos os applets estejam habilitados [cite: 5]. A verificação correta é:  
  `busybox --list | grep httpd` ou `busybox httpd --help` [cite: 5]
* **Hardware e fabricante:** A existência de `/storage/sdcard1` não é uma característica universal do KaiOS [cite: 5]. Ela depende da implementação do fabricante e do sistema de armazenamento utilizado pelo aparelho [cite: 5]. Da mesma maneira, o nome da interface de rede pode variar (não assumir que será sempre `wlan0`) [cite: 5].

## 12. Resumo

Um aparelho KaiOS que disponibiliza acesso ao ambiente Linux subjacente pode ser utilizado como um servidor HTTP local, desde que possua uma implementação de servidor adequada [cite: 5].

O BusyBox `httpd` é particularmente apropriado para esse tipo de experimento por ser compacto e oferecer uma configuração simples [cite: 5]:

```bash
busybox httpd -f -p 8080 -h /storage/sdcard1/www
```

O procedimento fundamental consiste em [cite: 5]:

1. Verificar a existência do applet `httpd` [cite: 5]; 
2. Criar um diretório específico para o conteúdo web [cite: 5]; 
3. Colocar os arquivos nesse diretório [cite: 5]; 
4. Iniciar o servidor em uma porta TCP [cite: 5]; 
5. Descobrir o endereço IP do aparelho [cite: 5]; 
6. Acessar o servidor a partir de outro dispositivo [cite: 5]; 
7. Utilizar `curl`, `ps` e ferramentas de rede para diagnóstico [cite: 5]. 

A principal vantagem para engenharia e desenvolvimento é que esse mecanismo pode transformar o próprio aparelho em uma pequena plataforma de servidor web, distribuição de arquivos, testes HTTP e experimentação de aplicações web, sem necessariamente modificar a ROM ou a camada Gecko [cite: 5].
