# Terminal de Sistema em KaiOS Modificado: Otimização de Uso por Teclas Físicas, Aliases e Menus de Inicialização

## 1. Visão geral

Em aparelhos KaiOS com acesso a `adb shell` e privilégios de root, um terminal de sistema pode ser utilizado para investigação, diagnóstico e execução de comandos diretamente no dispositivo [cite: 7].

Entretanto, aparelhos de baixo custo com teclado físico apresentam uma limitação prática importante: a entrada de comandos longos é lenta quando realizada exclusivamente pelas teclas alfanuméricas do aparelho [cite: 7].

Uma solução não é substituir o terminal existente, mas criar uma camada de conveniência sobre ele [cite: 7]. Essa camada pode utilizar:

* Aliases [cite: 7]; 
* Funções de shell [cite: 7]; 
* Scripts de automação [cite: 7]; 
* Menus interativos [cite: 7]; 
* Comandos pré-programados [cite: 7]; 
* Scripts de inicialização [cite: 7]; 
* Atalhos para operações recorrentes [cite: 7]. 

O objetivo é transformar operações que exigiriam vários caracteres em ações selecionáveis por poucas teclas [cite: 7].

No contexto investigado neste manual, essa abordagem é particularmente relevante para o Multilaser Zapp II, cujo firmware apresenta [cite: 7]:

```properties
ro.build.version.release=4.4.2
ro.build.version.sdk=19
ro.product.version_tag=kaios_2_5_modric_20200721_20
ro.product.model=ZAPP_II
ro.board.platform=mt6572
```

O kernel identificado é [cite: 7]:

```text
Linux version 3.4.67
```

Esses dados demonstram que o ambiente possui uma base Android antiga profundamente modificada para executar KaiOS [cite: 7]. Portanto, comandos e comportamentos documentados para Android moderno não devem ser automaticamente considerados aplicáveis [cite: 7].

## 2. Conceitos fundamentais

### 2.1 Terminal existente versus terminal personalizado

É importante distinguir duas abordagens [cite: 7]:

* **Terminal personalizado:** significa desenvolver uma nova interface ou aplicação de terminal [cite: 7].
* **Camada de conveniência:** significa utilizar o terminal que já existe e adicionar mecanismos para facilitar sua utilização [cite: 7].

Neste capítulo é adotada a segunda abordagem [cite: 7]. A estrutura conceitual é [cite: 7]:

```text
Teclas físicas
      │
      ▼
Terminal existente
      │
      ▼
Shell
      │
      ▼
Aliases / funções / scripts
      │
      ▼
Comandos do sistema
```

O terminal continua responsável pela interface, o shell continua executando os comandos, e os scripts apenas reduzem a quantidade de entrada necessária [cite: 7].

### 2.2 Alias

Um alias associa uma palavra curta a um comando maior [cite: 7]. Por exemplo:

```bash
alias si='getprop ro.build.display.id'
```

Depois disso, `si` pode executar o comando correspondente [cite: 7]. Aliases são especialmente úteis para comandos [cite: 7]:

* Longos [cite: 7]; 
* Executados frequentemente [cite: 7]; 
* Difíceis de digitar [cite: 7]; 
* Compostos por vários parâmetros [cite: 7]. 

Porém, aliases normalmente são uma característica do shell e da sessão atual [cite: 7]. Sua persistência depende de onde forem definidos [cite: 7].

### 2.3 Funções de shell

Funções são mais poderosas que aliases porque podem receber argumentos e executar várias operações [cite: 7]. Exemplo:

```bash
sysinfo() {
    getprop ro.product.model
    getprop ro.build.version.release
    getprop ro.build.display.id
}
```

A função pode então ser executada simplesmente com:

```bash
sysinfo
```

Uma função é mais apropriada quando uma operação precisa combinar vários comandos [cite: 7].

### 2.4 Scripts

Um script é um arquivo contendo comandos executáveis pelo shell [cite: 7]. Exemplo:

```bash
#!/system/bin/sh

echo "Modelo:"
getprop ro.product.model

echo "Build:"
getprop ro.build.display.id

echo "KaiOS:"
getprop ro.product.version_tag
```

Scripts são particularmente interessantes no Zapp II porque permitem criar ferramentas reutilizáveis sem modificar diretamente os componentes principais do sistema [cite: 7].

### 2.5 Menu de inicialização

Um menu pode funcionar como uma camada intermediária entre o usuário e o shell [cite: 7]:

```text
========================
     ZAPP II TOOLKIT
========================

1. Informações do sistema
2. Rede
3. Processos
4. Diagnóstico
5. Shell

Selecione:
```

O usuário precisa digitar somente uma opção, em vez de conhecer e digitar o comando correspondente [cite: 7]. Essa abordagem é especialmente adequada para aparelhos com teclado físico limitado [cite: 7].

## 3. Como funciona

Uma implementação simples pode seguir o seguinte fluxo [cite: 7]:

```text
Terminal
   │
   ▼
Script inicial
   │
   ├── 1 → diagnóstico
   ├── 2 → rede
   ├── 3 → informações
   ├── 4 → ferramentas
   └── 5 → shell interativo
```

O script pode utilizar `case` para selecionar uma operação [cite: 7]:

```bash
case "$opcao" in
    1)
        comando1
        ;;
    2)
        comando2
        ;;
    3)
        comando3
        ;;
esac
```

Essa técnica utiliza recursos básicos do shell e, portanto, tende a ser mais compatível com ambientes embarcados do que depender de frameworks ou bibliotecas adicionais [cite: 7].

### 3.1 Por que não substituir `/system/bin/sh`

Modificar diretamente o shell do sistema é uma estratégia desnecessariamente invasiva [cite: 7]. Por exemplo, substituir ou encapsular `/system/bin/sh` pode afetar [cite: 7]:

* Scripts de inicialização [cite: 7]; 
* Serviços [cite: 7]; 
* Comandos executados por outros processos [cite: 7]; 
* Scripts do firmware [cite: 7]; 
* Mecanismos de recuperação [cite: 7]; 
* Processos do próprio KaiOS [cite: 7]. 

Portanto, não é recomendável modificar `/system/bin/sh` apenas para criar um menu [cite: 7]. É preferível criar um executável ou script separado e configurar o terminal, quando isso for possível, para iniciar esse script [cite: 7].

## 5. Procedimentos práticos

### 5.1 Verificar qual shell está sendo utilizado

* **Objetivo:** Determinar qual interpretador está sendo executado antes de criar scripts dependentes de características específicas [cite: 7].

**Comando:**

```bash
adb shell 'echo $SHELL'
```

Também pode ser útil:

```bash
adb shell 'ls -l /system/bin/sh'
```

**Resultado esperado:**
O segundo comando deve mostrar o arquivo ou link utilizado como shell [cite: 7]. No ambiente investigado, o shell é fornecido pelo próprio firmware [cite: 7]. Não se deve assumir que seja equivalente a Bash [cite: 7].

**Diagnóstico:**
Verifique:

```bash
adb shell 'sh --help'
```

Caso `--help` não seja suportado, isso não significa necessariamente que o shell esteja com defeito [cite: 7]. Shells embarcados frequentemente possuem conjuntos de opções reduzidos [cite: 7].

### 5.2 Criar um primeiro script de diagnóstico

* **Objetivo:** Criar uma ferramenta simples que concentre informações frequentemente utilizadas durante a investigação [cite: 7].
* **Pré-requisitos:** Acesso ao terminal, permissão de execução e um diretório onde scripts possam ser armazenados [cite: 7].

Um local temporário comum para testes é `/data/local/tmp/` [cite: 7].

**Criar o script:**

```bash
cat > /data/local/tmp/sysinfo.sh <<'EOF'
#!/system/bin/sh

echo "=== SISTEMA ==="
getprop ro.product.model
getprop ro.product.manufacturer
getprop ro.build.version.release
getprop ro.build.version.sdk

echo
echo "=== BUILD ==="
getprop ro.build.display.id
getprop ro.build.id
getprop ro.build.fingerprint

echo
echo "=== KAIOS ==="
getprop ro.product.version_tag

echo
echo "=== KERNEL ==="
uname -a
EOF
```

Depois:

```bash
chmod 755 /data/local/tmp/sysinfo.sh
```

Executar:

```bash
/data/local/tmp/sysinfo.sh
```

**Resultado esperado:**
O script deve produzir um resumo das propriedades principais do sistema [cite: 7].

**Como desfazer:**

```bash
rm /data/local/tmp/sysinfo.sh
```

Esse procedimento não modifica a ROM [cite: 7]. O arquivo criado pode ser removido posteriormente [cite: 7].

### 5.3 Criar aliases

* **Objetivo:** Reduzir comandos frequentemente utilizados durante a investigação [cite: 7].

Exemplo:

```bash
alias build='getprop ro.build.display.id'
alias kaios='getprop ro.product.version_tag'
alias kernel='uname -a'
alias model='getprop ro.product.model'
```

Agora `build`, `kaios`, `kernel` e `model` podem substituir comandos mais longos [cite: 7].

**Limitação importante:**
O alias pode desaparecer quando a sessão do shell terminar [cite: 7]. Para torná-lo persistente, é necessário identificar qual arquivo de inicialização o shell utilizado pelo firmware realmente lê [cite: 7]. Não se deve presumir que `/system/etc/profile` ou `/system/etc/mkshrc` sejam utilizados sem verificar o comportamento do firmware [cite: 7].

### 5.4 Identificar arquivos de inicialização do shell

Antes de modificar qualquer arquivo, é preferível procurar referências ao shell [cite: 7]. Exemplos:

```bash
ls -la /system/etc/
```

e:

```bash
find /system/etc -maxdepth 2 -type f 2>/dev/null
```

Dependendo das ferramentas disponíveis, pode-se procurar por arquivos conhecidos:

```bash
find /system -name 'profile' 2>/dev/null
```

ou:

```bash
find /system -name '*shrc*' 2>/dev/null
```

O resultado precisa ser analisado antes de qualquer alteração [cite: 7]. A existência de um arquivo não prova que ele seja carregado pelo shell [cite: 7].

### 5.5 Criar um menu interativo

* **Objetivo:** Reduzir ainda mais a necessidade de digitação [cite: 7].

Um exemplo minimalista:

```bash
#!/system/bin/sh

while true
do
    clear

    echo "===================="
    echo "    ZAPP II TOOL"
    echo "===================="
    echo
    echo "1 - Sistema"
    echo "2 - Kernel"
    echo "3 - Rede"
    echo "4 - Shell"
    echo "5 - Sair"
    echo
    echo -n "Opcao: "

    read opcao

    case "$opcao" in
        1)
            getprop ro.product.model
            getprop ro.build.display.id
            getprop ro.product.version_tag
            echo
            echo "Pressione Enter..."
            read pausa
            ;;

        2)
            uname -a
            echo
            echo "Pressione Enter..."
            read pausa
            ;;

        3)
            ifconfig
            echo
            echo "Pressione Enter..."
            read pausa
            ;;

        4)
            exec /system/bin/sh
            ;;

        5)
            exit 0
            ;;

        *)
            echo "Opcao invalida."
            sleep 1
            ;;
    esac
done
```

O uso de `exec /system/bin/sh` é conceitualmente importante [cite: 7]. Em vez de iniciar outra camada desnecessária, o processo atual pode ser substituído por um shell [cite: 7].
A disponibilidade de `clear`, `sleep`, `ifconfig` e outros comandos deve ser verificada no firmware específico [cite: 7].

## 6. Exemplos

### 6.1 Menu especializado em diagnóstico

Em vez de criar um menu genérico, pode-se criar um menu voltado especificamente para o trabalho de engenharia do aparelho [cite: 7]:

```text
ZAPP II DEBUG

1  Build
2  Kernel
3  Input
4  Bluetooth
5  USB
6  Processos
7  Shell
0  Sair
```

Por exemplo, a opção 3 poderia executar `cat /proc/bus/input/devices` [cite: 7]. Isso é particularmente útil porque esse arquivo permitiu verificar anteriormente os dispositivos de entrada presentes no Zapp II [cite: 7].

### 6.2 Atalho para propriedades KaiOS

Uma função:

```bash
kaiosinfo() {
    echo "KaiOS:"
    getprop ro.product.version_tag

    echo "Build:"
    getprop ro.build.display.id

    echo "Android base:"
    getprop ro.build.version.release

    echo "SDK:"
    getprop ro.build.version.sdk
}
```

Pode ser chamada com `kaiosinfo` [cite: 7]. No firmware analisado, isso permite obter rapidamente [cite: 7]:

```text
kaios_2_5_modric_20200721_20
4.4.2
19
```

### 6.3 Atalhos para investigação de dispositivos de entrada

Uma função útil durante investigação:

```bash
inputs() {
    cat /proc/bus/input/devices
}
```

Depois, basta executar `inputs` [cite: 7]. Esse tipo de função é preferível a criar uma implementação própria de entrada, pois apenas encapsula uma ferramenta de diagnóstico já existente [cite: 7].

## 7. Problemas comuns

* **Alias desaparece**  
  *Causa provável:* o alias foi criado somente na sessão atual [cite: 7].  
  *Solução:* identificar o arquivo de inicialização efetivamente utilizado pelo shell [cite: 7].

* **`read` não funciona como esperado**  
  Algumas implementações de shell embarcado podem apresentar diferenças em relação ao Bash [cite: 7].  
  *Testar:*
  ```bash
  read teste
  echo "$teste"
  ```
  Se houver comportamento inesperado, o script deve ser adaptado ao shell disponível [cite: 7].

* **`clear` não existe**  
  *Verifique:* `which clear` ou `ls -l /system/bin/clear` [cite: 7].  
  Se não existir, o menu pode simplesmente não limpar a tela [cite: 7]. Isso não impede o funcionamento do restante do script [cite: 7].

* **Script não executa**  
  *Verifique:* `ls -l /data/local/tmp/script.sh` e `chmod 755 /data/local/tmp/script.sh` [cite: 7].  
  Também é possível executá-lo explicitamente:
  ```bash
  /system/bin/sh /data/local/tmp/script.sh
  ```
  Essa forma elimina a necessidade de o sistema reconhecer o shebang [cite: 7].

* **Comando existe no ADB, mas não no terminal**  
  Isso pode ocorrer por diferenças de PATH, usuário, permissões, ambiente, diretório atual ou shell utilizado pelo terminal [cite: 7].  
  Compare `echo "$PATH"` no terminal e no ADB [cite: 7]. Também é possível executar comandos usando caminhos absolutos quando conhecidos [cite: 7].

## 8. Diagnóstico e debugging

A primeira regra ao desenvolver ferramentas para esse ambiente é não modificar o sistema antes de entender seu comportamento [cite: 7].

### 8.1 Verificar o ambiente

```bash
id
whoami
echo "$PATH"
uname -a
getprop ro.build.display.id
```

Esses comandos permitem registrar as condições sob as quais o script está sendo executado [cite: 7].

### 8.2 Verificar comandos disponíveis

Em vez de assumir que uma ferramenta existe [cite: 7]:

```bash
which comando
```

ou:

```bash
ls -l /system/bin/comando
```

O firmware do Zapp II demonstrou anteriormente que alguns utilitários esperados em sistemas Linux completos não estão disponíveis (por exemplo, o comando `file` não estava instalado) [cite: 7]. Portanto, scripts destinados a esse aparelho devem evitar dependências desnecessárias [cite: 7].

### 8.3 Registrar a saída

Durante desenvolvimento, pode ser útil:

```bash
/data/local/tmp/teste.sh > /data/local/tmp/teste.log 2>&1
```

Isso permite preservar tanto a saída normal quanto os erros [cite: 7]. Depois:

```bash
cat /data/local/tmp/teste.log
```

Esse método é especialmente útil quando o terminal apresenta limitações de visualização [cite: 7].

### 8.4 Preservar evidências

Durante engenharia reversa, não é recomendável editar diretamente arquivos importantes do sistema apenas para testar uma hipótese [cite: 7]. É preferível [cite: 7]:

1. Copiar o arquivo [cite: 7]; 
2. Modificar a cópia [cite: 7]; 
3. Testar [cite: 7]; 
4. Registrar o resultado [cite: 7]; 
5. Somente então considerar uma alteração permanente [cite: 7]. 

Por exemplo:

```bash
cp arquivo_original arquivo_backup
```

A localização e as permissões precisam ser verificadas antes de qualquer operação de cópia [cite: 7].

## 9. Segurança e riscos

Scripts de conveniência são relativamente seguros quando permanecem em áreas temporárias, mas o risco aumenta significativamente quando passam a modificar componentes do sistema [cite: 7].

### Baixo risco
Exemplos em `/data/local/tmp/`. Scripts que apenas executam `getprop`, `uname`, `cat` e `ls` tendem a ser operações de leitura [cite: 7].

### Risco maior
Alterações em `/system/bin/`, `/system/etc/`, `/system/app/` e `/system/framework/` podem causar consequências inesperadas [cite: 7]. Particularmente perigoso é substituir `/system/bin/sh` ou modificar scripts de inicialização [cite: 7]. Uma alteração incorreta pode impedir a inicialização de processos essenciais ou produzir um sistema parcialmente inutilizável [cite: 7].

**Regra prática:**
Para uma interface de conveniência, a arquitetura preferencial deve ser [cite: 7]:

```text
ROM original
    │
    ├── Terminal existente
    │
    └── Script externo
           │
           ├── aliases
           ├── funções
           └── menu
```

e não:

```text
ROM original
    ↓
substituição do shell
    ↓
modificação de componentes essenciais
```

## 10. Compatibilidade

A compatibilidade depende de diversos fatores [cite: 7]:

| Fator | Impacto |
| :--- | :--- |
| **Versão do KaiOS** | APIs e componentes podem mudar |
| **Base Android** | Define ferramentas e estrutura disponíveis |
| **Shell** | Determina sintaxe suportada |
| **Fabricante** | Pode remover comandos e modificar caminhos |
| **Chipset** | Afeta drivers e interfaces de hardware |
| **Terminal utilizado** | Determina como o shell é iniciado |
| **Root** | Determina quais operações podem ser executadas |
| **PATH** | Determina quais comandos podem ser chamados diretamente |

No Zapp II analisado, há evidências concretas de um ambiente bastante específico [cite: 7]:

* **Android:** 4.4.2 [cite: 7]
* **SDK:** 19 [cite: 7]
* **Kernel:** 3.4.67 [cite: 7]
* **SoC:** MT6572 [cite: 7]
* **KaiOS tag:** `kaios_2_5_modric_20200721_20` [cite: 7]
* **Build:** `ML-SI04_ZAPP_II.V14_240730_1535` [cite: 7]

Esses dados não devem ser generalizados para todos os aparelhos KaiOS [cite: 7]. Além disso, a ausência de determinados comandos ou interfaces não significa necessariamente que o recurso correspondente não exista no sistema (por exemplo, `/proc/config.gz` não estava disponível no Zapp II, mas isso por si só não permite concluir quais opções foram utilizadas na compilação do kernel) [cite: 7].

## 12. Resumo

O uso de um terminal em um aparelho KaiOS com teclado físico limitado pode ser significativamente melhorado sem modificar o terminal ou desenvolver uma nova aplicação [cite: 7].

As principais técnicas são [cite: 7]:

1. Aliases para comandos curtos e recorrentes [cite: 7].
2. Funções de shell para operações compostas [cite: 7].
3. Scripts para automatizar procedimentos [cite: 7].
4. Menus numéricos para reduzir a necessidade de digitação [cite: 7].
5. Scripts de diagnóstico para concentrar comandos utilizados frequentemente [cite: 7].
6. Execução através de caminhos absolutos quando o PATH for inconsistente [cite: 7].
7. Uso de `/data/local/tmp/` durante desenvolvimento, reduzindo alterações permanentes no sistema [cite: 7].
8. Preservação de evidências e backups antes de modificar componentes importantes [cite: 7].
9. Evitar alterações em `/system/bin/sh` quando uma solução externa for suficiente [cite: 7].

Para o Zapp II, a abordagem mais segura e prática é construir progressivamente uma pequena suíte de ferramentas de shell, começando por scripts de diagnóstico e menus simples e somente posteriormente avaliando mecanismos de inicialização automática [cite: 7].
